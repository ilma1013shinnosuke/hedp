# 002 共通Execution層を採用する

- 状態: 採用
- 決定日: 2026-07-24

## 背景

Smart LEDZ、Qrio、SwitchBot、BRAVIA、エコキュートなどは、通信方法、応答、確認方法、
再試行時の危険性が異なる。一方で、対象確認、権限、安全条件、重複抑止、期限、結果確認、
監査、再起動後の同期は共通して必要である。

個別Adapterから直接操作すると、機器が増えるたびに安全規則が重複し、同じ依頼に対して
異なる結果表記や再試行動作が生じる。

## 決定

SumiCoreの4層設計における④操作・実行として、最小の共通Execution層を採用する。

- ③や利用者はメーカー非依存のIntentを作る。
- Execution層がPolicy、期限、対象、重複、実行計画、確認、監査を担当する。
- Adapterはメーカー固有の変換、通信、エラー整理、読み取りを担当する。
- 送信記録と実状態の確認結果を分ける。
- 処理の進行段階Phaseと最終結果Outcomeを分ける。
- 複数対象は親子Operationで表し、一部成功と結果不明を正式な結果として扱う。
- 再起動後は現在状態を同期するまで送信せず、古い命令を再生しない。
- 機器自律を基本とし、SumiCore依存機能は理由と停止時動作を明示する。

詳細な契約は[共通Execution層 基本設計](../execution-contract.md)を正とする。

## 採用理由

- メーカーが増えても安全規則と監査方法をそろえられる。
- 「命令を送った」と「実際に成功した」を混同しない。
- 危険度の異なる操作へ、機器・能力別の再試行方針を適用できる。
- Shadow Modeから段階的に本番へ移行できる。
- Adapter更新の影響を共通部分から分離できる。

## 影響

- 本番の書き込み操作は、原則として共通Execution層を通す。
- 既存の調査用操作コードは自動的に本番対応とはみなさない。
- 最初の実装では共通契約と一つの低リスク機能だけを扱う。
- 実装開始時に専用監査台帳が必要になる可能性があるが、本決定だけではDBを変更しない。

## 採用しなかった案

### Adapterごとに安全処理を実装する

短期的には速いが、結果表記、再試行、権限、監査が機器ごとに分かれ、長期保守が難しい。

### 最初から汎用ワークフロー基盤を作る

現時点では実利用に必要な範囲が確定しておらず、複雑さが先行するため採用しない。

### すべての機器を同じ再試行規則にする

センサー読み取りと解錠・給湯Triggerでは再送時の危険性が異なるため採用しない。
