# 004 Adapterの調査・実装・運用手順を統一する

- 状態: 採用
- 決定日: 2026-07-25

## 背景

家庭機器は、通信方式、認証、取得周期、保存量、操作危険度、結果確認方法が異なる。
機器ごとに場当たり的な調査と実装を行うと、秘密情報、実機変更、Raw保存、再試行、
運用監視、廃止方法が不統一になる。

一方、すべてのAdapterを同じ構造へ先に作り替えると、使わない抽象化と空フォルダが増え、
現役システムを複雑にする。

## 決定

[メーカー別Adapterの調査・実装・運用手順](../adapter-lifecycle.md)を採用する。

- 目的、公開調査、実機試験計画、隔離観測の順に進める。
- 詳細な禁止事項は公開調査後に決めるが、高影響操作は最初から承認必須とする。
- 読み取りと操作は、公開機能と実行経路を完全に分ける。
- 副作用のない認証、接続、通信、エラー処理は共有できる。
- ①情報収集は読み取り、④操作・実行は操作だけを利用する。
- 操作が不要なAdapterは読み取り専用で完成とする。
- 実Rawは隔離・上限付きで扱い、匿名fixtureだけをGitへ追加する。
- 操作は能力単位で定義し、Shadow Modeから段階導入する。
- Adapterの状態、監視、仕様変更、停止、廃止を同じ手順で管理する。
- 既存Adapterを一括移動せず、次の実改修から適用する。

## 採用理由

- 実機へ触れる前に影響と停止条件を確認できる。
- 読み取り障害と操作障害を分離できる。
- 操作コードが収集経路へ混入することを防げる。
- 新しいメーカーでも保存量、失敗、更新、廃止まで確認できる。
- 実際に必要と判明した共通部分だけを残せる。

## 影響

- 新しい機器調査には目的、根拠区分、安全計画、能力表、データ辞書が必要になる。
- 操作機能は読み取り完成後、価値が確認できた能力だけに追加する。
- 将来の新規Adapterでは、収集経路から`executor`へ依存しないことをテストする。
- この決定だけでは新しいフォルダ、DB表、共通基底クラスを作らない。

## 採用しなかった案

### 調査前にすべての機器固有禁止事項を決める

公開仕様を知らずに正確な影響を判断できないため、初期防護線と調査後の詳細条件に分ける。

### 読み取りと操作を一つの公開Clientへまとめる

収集処理から誤って操作機能を呼べるため採用しない。内部の副作用のない通信処理だけを共有する。

### 全Adapterを直ちに同じファイル構成へ移す

利用価値のない整理と回帰リスクが増えるため、実改修時に段階適用する。
