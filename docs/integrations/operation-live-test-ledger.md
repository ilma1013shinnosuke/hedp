# 操作用Adapter 実機試験台帳

## 位置付け

本書は[操作用Adapter 適格性確認計画](operation-qualification-plan.md)に従い、
機器・能力ごとの現在段階と、次に承認を得る単発試験だけを管理する台帳である。
共通Execution契約は[Execution層 共通契約](../execution-contract.md)を正本とし、
本書を実機操作、常駐化、設定変更の包括承認には使用しない。

実機へ送信する前に、試験ごとに次の5項目を利用者へ提示し、その試験だけの明示承認を得る。

1. 対象
2. 送信する正確な命令
3. 物理的・運用上の影響
4. 結果の確認方法
5. 原状復帰方法

原状復帰も別の書き込み操作である。前進操作の成功を読み戻しで確認できた場合だけ、
事前に承認された復元命令を送る。結果不明時は逆命令を自動送信せず、読み取りと利用者確認へ戻る。

## 現在の共通判定

- Stage 0の匿名fixture・dry-run・Shadow Modeは継続可能。
- SwitchBot E26／テープライト3には共通ExecutionGate配下のlive portを実装済み。
  実機での適格性確認が終わるまでは、ほかの能力と同じく実機試験前として扱う。
- Readerが未合格、状態が`stale`、`missing`、`invalid`、`unknown`、対象能力が未確認の場合は送信しない。
- 一Intentにつき書き込みは最大一回。timeout、通信断、結果不明を理由に再送しない。
- 実機設定、登録、firmware、network、認証、保守設定は本台帳の対象外とする。

## Adapter別の既知の境界

- SwitchBot照明の直接runnerは診断専用で、本番UI利用を禁止する。照明の本番経路は
  `FastLightExecutionPort`を共通Executionの`LIVE` modeから呼ぶ。
- SwitchBot掃除機、FusionSolarはfixture明示のないoperation transportを拒否する。
- Smart LEDZ、BRAVIA、Miele、日産サクラはlive dispatchを公開していない。
- Smart LEDZのschedule選択は未検証であり、実機試験候補にしない。
- 日産サクラの解錠は未対応であり、実機試験候補にしない。
- Mieleは開始後の停止・取消経路が未定義のため、単発試験へ進めない。
- エコキュートの低水準Setを直接呼ばず、typed requestと共通Executionを経由させる。
- Qrioのwrite portは、永続registryと共通Executionへの接続完了まで実機へ使わない。

## 最初の候補：SwitchBot E26 明るさ単発試験

### 現在の準備状態

この試験は、低リスク候補として承認用の試験票まで具体化した。現在は
`FastLightExecutionPort`が共通`ExecutionCoordinator`の`LIVE` modeからだけ呼び出せる。
一方、診断用CLIは共通Gateを意図的に通らないため、本番UI・自動化からの利用を禁止する。
正式な通常操作は、下記のReader、能力、Evidence、Authorizationの条件を満たす場合だけ
共通Execution経路から送信できる。

次のすべてを満たすまで、利用者へ実行承認を求めず、音による通知も行わない。

1. E26の匿名aliasと`deviceType`が、上限付きread-only取得で一致している。
2. `power`と`brightness`が`good`かつfreshで、観測時刻が確認できる。
3. E26に`SET_BRIGHTNESS`能力があることを実機能力情報から確認している。
4. 共通Executionへ、E26だけを対象とするlive portが登録されている。
5. live portをCollector、Reader、UIから直接呼べないことを契約試験で確認している。
6. Stage 1 Shadowで、同一Intentが`would_dispatch`となり、期限切れ、重複、別対象、
   stale、低品質、手動介入中が送信前に止まる。
7. 読み戻し経路が書き込み経路と分離され、一回の書き込みに対して上限付きで確認できる。

### 対象と正確な命令

| 項目 | 試験値 |
|---|---|
| 対象 | read-only取得で同一性を確認した、登録済みE26の匿名alias一台 |
| 能力 | `switchbot-light-state-set` |
| 命令 | `LightCommand.SET_BRIGHTNESS`による明るさ絶対値指定 |
| 事前状態 | 電源`on`、明るさ`B`、両フィールド`good`かつfresh |
| 試験値 | `B <= 80`なら`T = B + 10`、それ以外は`T = B - 10` |
| 値の制限 | `T`は`10..90`に含め、`0`と`100`を使用しない |
| Intent期限 | 作成から60秒以内 |
| 書き込み上限 | 一Intent、一対象、一能力、一回 |
| 確認上限 | 書き込み後10秒以内、最大3回のread-only確認 |
| 物理的影響 | 最大10ポイントの一時的な明るさ変化。電源状態は変更しない |
| 復元目標 | 事前に取得した明るさ絶対値`B` |

内部では、次と同じ意味の型付き要求だけを使用する。`operation_id`と`target_alias`は
安全な不透明参照であり、家庭固有IDやメーカーの機器IDを使用しない。

```python
LightOperationRequest(
    operation_id="<one-time-safe-operation-ref>",
    target_alias="<confirmed-e26-anonymous-alias>",
    desired_state=LightDesiredState(
        LightCommand.SET_BRIGHTNESS,
        T,
    ),
    requested_at="<timezone-aware-current-time>",
    dry_run=False,
)
```

メーカー固有payload、endpoint、token、実機IDを試験票や監査要約へ記録しない。

### 事前確認

- 利用者が在宅し、対象照明を直接確認できる。
- 利用者が純正アプリ、物理スイッチ、音声操作を行っていない。
- 同じ照明に対する未完了Intent、schedule、scene、自動化がない。
- Readerが取得した匿名alias、`deviceType`、`power=on`、`brightness=B`が一致する。
- capability snapshotが期限内で、`SET_BRIGHTNESS`を含む。
- 直前のread-only状態と、承認画面に表示した`B`が一致する。
- `T != B`であり、実行時点の時刻がIntentとAuthorizationの期限内である。
- 手動復旧として、純正アプリまたは物理操作を利用できる。

電源が`off`、明るさが欠損、deviceTypeが未確認、事前状態が変化している場合は、
点灯命令へ自動的に置き換えず、この試験を延期する。

### 結果確認と分類

1. 共通ExecutionGateの許可結果を記録する。
2. live portへの書き込み呼び出しが一回だけであることを記録する。
3. メーカー受付は`accepted`として記録し、完了とは扱わない。
4. read-only Readerで、書き込み後に観測されたfresh/goodの`brightness`を確認する。
5. `T`と一致した場合だけ、前進操作を`completed`とする。
6. 一致後に限り、同じ承認票に含まれる復元Intentで`B`を一回だけ指定する。
7. 復元後もread-only Readerでfresh/goodの`brightness=B`を確認する。

| 状況 | outcome | 次の処理 |
|---|---|---|
| Gateで拒否 | `blocked` | 書き込まず終了 |
| 受付拒否 | `failed` | 再送せず終了 |
| 受付後に`T`と一致 | `completed` | 承認済み復元へ進める |
| fresh/goodだが`T`と不一致 | `failed` | 復元命令を自動送信せず利用者確認 |
| timeout、通信断、読み戻し不能 | `unknown` | 再送・自動復元せず、読み取りと物理確認だけ |
| 対象、kind、観測時刻、品質が不一致 | `unknown` | 即時中止し対象再同期 |
| 復元後に`B`と一致 | `restored` | 試験終了 |
| 復元受付後に確認不能 | `unknown` | 追加書き込みせず利用者確認 |

### 即時中止条件

- 利用者が停止を求めた。
- 承認時から対象状態、alias解決、能力、電源、明るさが変化した。
- 手動操作、純正アプリ操作、scene、schedule、自動化を検出した。
- Readerまたはcapabilityが`stale`、`missing`、`invalid`、`unknown`になった。
- 別の機器または別のkindからの応答を受けた。
- 書き込み呼び出し回数が一回を超えるおそれがある。
- 受付状態、読み戻し、観測時刻の意味を解釈できない。
- 利用者の目視とReaderの値が一致しない。

中止後は実機へ別命令を送らない。利用者による目視、純正アプリまたは物理操作と、
read-only Readerの再同期で状態を確定する。

### 実行直前に提示する承認文

> 対象：登録済みSwitchBot E26一台（匿名aliasで確認済み）
>
> 命令：電源は変えず、明るさを現在の`B%`から`T%`へ一回だけ変更します。
>
> 影響：目で分かる小さな明るさ変化が最大30秒程度発生します。
>
> 確認：送信受付と実状態を分け、10秒以内・最大3回の読み取りで`T%`を確認します。
>
> 復元：`T%`を確認できた場合だけ、事前値`B%`へ一回だけ戻して再確認します。
>
> 安全策：timeout、結果不明、不一致では再送も自動復元もしません。純正アプリまたは
> 物理操作で確認できる状態で行います。この一回の試験を実行してよいですか。

`B`と`T`は実行直前のfresh/goodなread-only結果から確定し、承認文の提示後に値が変化したら
その承認を使用しない。

## 次候補：テープライト3 明るさ単発試験

2026-07-27の上限付きread-only確認で、登録種類`Strip Light 3`と、電源、明るさ、
RGB、色温度、online状態の取得項目を確認した。家庭固有IDとRaw値は記録していない。
正式なReader、機種別Writer、ExecutionGate接続、上限付き試験runner、匿名結果、
オフライン回帰試験は準備済みである。

初回試験は、実行時のread-only結果が`Strip Light 3`、点灯中、明るさ5〜95%の場合だけ、
現在値から5ポイント上げる。反映確認後、直ちに元の絶対値へ戻し、最終read-backを行う。
読み取り最大7回、書き込み最大2回で、自動再送しない。送信結果が不明でも最初の命令だけ
届いた可能性があるため、元値への復元を一度試みる。

消灯中、境界値、型不一致、欠損、不正応答、Gate拒否、確認不一致、復元失敗では停止する。
電源、色、色温度、シーン、登録、firmware、設定は変更しない。E26の承認は流用せず、
この試験票について利用者の明示承認を得るまで命令を送信しない。

## 結果の記録方法

実機試験を行う場合は、秘密値と家庭固有情報を除き、次だけを追記する。

- 日時、匿名対象、能力、試験段階
- 承認された命令の意味と期限
- 事前状態の品質・鮮度
- Gate判定、送信受付、読み戻し、最終outcome
- 反映時間、確認回数、結果不明の有無
- 原状復帰結果または手動復旧結果
- 中止理由、次回へ持ち越す未確認事項

認証header、endpoint、IP、MAC、機器ID、車両識別子、入退室履歴、実通信Rawは記録しない。

## 2026-07-27 SwitchBot E26 1%刻み消灯試験

- 対象: 匿名alias `e26-smart-bulb`
- 事前状態: 点灯、明るさ100%、Reader資格確認済み
- 実施内容: 99%から1%まで1ポイントずつ、合計99回の明るさ指定を送信
- 時間計画: 開始から9.9秒まで0.1秒間隔で減光し、10.0秒時点で消灯命令を送信
- 受付結果: 明るさ指定99回と消灯命令はすべて受付
- 実際の消灯時点: 自動計測なし。確定記録は「開始10.0秒後に消灯命令送信」
- 読み戻し: 試験直後のクラウド状態では消灯を確定できず、結果は一時的に`unknown`
- 色温度: 消灯後の応答では検証できないため、変更なしとは断定しない
- 他機器への操作: なし
- 補足: 今後、物理消灯までの所要時間を記録する場合は、命令送信時刻と実機変化の観測時刻を
  別々に計測する。今回の10.0秒は命令送信までの時間であり、物理反映遅延を含まない。

## 2026-07-27 SwitchBot テープライト3 直接操作確認

- 対象: 匿名alias `strip-light-3`
- 実施能力: 点灯、明るさ、RGB、色温度
- 確認した命令: 2700K、RGB赤・青・緑、RGB白、明るさ100%、点灯、6500K
- 受付結果: 上記の個別命令と、RGB白・100%・点灯の連続3命令はすべてメーカー受付
- 追加試験: RGB白に白色LED側を加える意図で、点灯、RGB白、6500K、100%を順次送信し、
  4命令すべてメーカー受付
- 受付時間: 単発RGB・色温度命令はおおむね0.14〜0.20秒
- 目視確認: RGB赤・青・緑の色変化は利用者が確認
- 目視結果: RGB白と色温度命令の連続送信後も、白色LEDは点灯していなかった
- 単色確認: RGB赤、100%、点灯だけを送った試験では、利用者の目視で赤色LEDだけが点灯し、
  白色LEDは点灯しなかった
- 虹色sequence: RGBだけを使い、赤、橙、黄、緑、水色、青、紫を3秒間隔で2周した。
  14回の色指定はすべてメーカー受付となり、白色LED・色温度命令は送っていない
- RGB連続補間: 赤、青、緑、赤の各遷移を72段階に分けて3周した。開始色を含む649命令は
  すべてメーカー受付となり、9遷移・3周を完了した。白色LED・色温度命令は送っていない。
  これはクラウド経路の負荷試験も兼ねた一時的な実機試験であり、通常UIの送信頻度には採用しない
- 白色減光: 色温度6500K、明るさ100%、点灯を送り、3秒保持した後、99%から1%まで
  1ポイントずつ待機なしで下げ、最後に消灯した。合計103命令はすべてメーカー受付となり、
  開始から消灯命令受付まで10.6秒だった。RGB命令は送っていない。物理消灯時刻は自動計測して
  いないため、10.6秒は物理反映時間ではなく全命令の受付完了時間である
- 結論: 現在の公開API高速経路では、RGBと白色LEDの同時点灯を対応能力として公開しない
- 利用者判断: 同時点灯は不要。想定外の消費電力を避けるため、専用アプリ、BLE、非公開命令を
  使った追加探索は行わない
- 保存: 秘密値、家庭固有ID、endpoint、実通信Rawは保存していない
