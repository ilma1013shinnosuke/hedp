# SwitchBot テープライト3 高速直送経路

利用者が明示した照明操作を低遅延で送るための、テープライト3専用出力ポートである。
通常操作では機器一覧や現在状態を先に取得せず、署名済みPOSTを1回だけ送る。

正式な能力、Gate、fast execute、分離read-back、安全停止の正本は
[正式操作Adapter](switchbot-strip-light-3-formal-adapter.md)とする。本書の直接runnerは
引き続き診断専用であり、HESTIA UIの正式入口ではない。

## 確認済み能力

2026-07-27の上限付きread-only確認で、登録種類`Strip Light 3`と、電源、明るさ、
RGB、色温度、online状態の取得項目を確認した。公式OpenAPI文書でも、点灯・消灯、
明るさ0〜100%、RGB各0〜255、色温度2700〜6500Kの命令が定義されている。

## 速度と安全の境界

- 正式UIはAIやチャットを通さず、保持済みの送信ポートへ直接命令する。
- UI起動時に送信ポートを一度生成し、HTTP sessionを操作間で再利用する。
- スライダーは表示を即時更新し、50〜100ms単位で最後の値だけを送る。
- 通常の単発操作は事前読取・事後読取・自動再試行を行わない。
- 到達不能やtimeoutを成功扱いせず、同じ操作を自動で二重送信しない。
- 匿名alias、命令、受付成否、受付時間、試行回数だけを記録する。
- 秘密値、家庭固有機器ID、Raw応答はログ、回答、Gitへ出さない。
- `FastLightControlSession`が操作を直列化し、スライダーの未送信旧値を破棄する。
- `FastLightExecutionPort`は共通`ExecutionCoordinator`の`LIVE` modeからだけ呼ぶ。
- ExecutionGateは、短期Authorization、freshなキャッシュ済みEvidence、対象能力、
  手動介入、期限、重複operation IDを通信前に検査する。
- メーカー受付後は`pending_verification`とし、物理反映の確認は独立Readerが非同期に行う。

クラウド経路を使うため物理反映時間は保証しない。受付時間を継続計測し、将来の
ローカルBLE経路が正式適格となった場合も、同じ公開interfaceの内側だけを差し替える。

## 一度だけ行う紐付け

`scripts/configure_switchbot_strip_light_fast_path.py`は登録一覧を1回取得し、
`deviceType`が`Strip Light 3`の機器が正確に1台の場合だけ、mode 0600の`.env`へ
家庭固有機器IDを保存する。0台または複数台なら`.env`を変更せず失敗する。

実行時は`SWITCHBOT_TOKEN`、`SWITCHBOT_SECRET`、
`SWITCHBOT_STRIP_LIGHT_3_DEVICE_ID`を使用し、値は表示しない。

## 実装上の分離

読み取りは既存の`SecondaryFleetProbe`と正規化処理、操作は
`StripLight3FastCommandTransport`、共通Gateへの接続は`FastLightExecutionPort`、
常駐とスライダー集約は`FastLightControlSession`が担当する。機器固有のBindingと
通信処理はAdapter内に閉じ、UIや第3層は家庭固有IDやOpenAPIの形式を知らない。

`strip_light_fast_runner.py`は診断用の単発入口であり、本番UIから直接呼ばない。
本番UIは常駐sessionだけを使い、操作ごとのPythonプロセス起動を行わない。

## 初回実機適格性試験

初回の状態変更試験は
`hedp.operations.switchbot_strip_light_live_trial`を使用し、通常操作より厳しい上限を
設ける。

- 実行前にread-onlyで`deviceType`、電源、明るさを確認する。
- `deviceType`が`Strip Light 3`で、点灯中、明るさが5〜95%の場合だけ続行する。
- 現在の明るさから5ポイントだけ上げ、共通ExecutionGateを通して1回送信する。
- 上限付きread-backで反映を確認し、直ちに元の明るさを1回送信して復元する。
- 復元後も上限付きread-backで元の値へ戻ったことを確認する。
- 読み取りは最大7回、書き込みは「変更」と「復元」の最大2回で、自動再送しない。
- 最初の送信結果が不明でも、命令だけ届いた可能性があるため復元を1回試みる。
- 電源、RGB、色温度、シーン、登録、firmware、設定は変更しない。
- device type不一致、消灯中、境界値、欠損、不正応答、Gate拒否、復元失敗では停止する。
- 秘密値、家庭固有機器ID、実際の明るさ、Raw応答を結果へ含めない。

この試験runnerは、利用者が対象・影響・確認・復元・中止条件を確認して明示承認した
一回の試験だけに使用する。本番UIの通常操作入口にはしない。

## 2026-07-27 直接操作で得た知見

利用者が実機を見られる状態で、テープライト3へ高速直送経路から次の命令を送った。
家庭固有ID、認証情報、endpoint、実通信Rawは記録していない。

- 色温度2700K: メーカー受付を確認した。
- RGB赤、青、緑: それぞれメーカー受付を確認し、利用者が色変化を目視確認した。
- RGB赤、明るさ100%、点灯: 色温度命令を送らず、`255:0:0`、100%、点灯を順次送信した。
  3命令はすべてメーカー受付となり、利用者の目視で赤色LEDだけが点灯し、白色LEDは
  点灯しなかったことを確認した。
- RGB白、明るさ100%、点灯: 点灯、`255:255:255`、100%の順で送り、3命令すべての
  メーカー受付を確認した。
- RGB白へ色温度6500Kを追加する試験: 点灯、RGB白、6500K、100%の順で送り、4命令
  すべてのメーカー受付を確認した。

単発のRGB・色温度命令は、HTTP受付までおおむね0.14〜0.20秒だった。ただし、
チャット入力から物理反映までの時間にはAI処理とプロセス起動時間が加わる。本番UIは
常駐送信sessionから直接呼び、操作前の状態取得を行わない。

利用者の目視では、白色LED（色温度mode）は点灯時に本体側のフェードが必ず入り、
最大の明るさへ達するまで約1秒を要した。一方、RGB modeは色指定後にほぼ瞬時に点灯した。
高速直送経路の通信遅延とは別の機器側挙動として扱い、白色LEDの瞬時点灯を保証しない。
点滅など立ち上がり時間が重要な表現ではRGB modeを優先する。

OpenAPIはRGBと色温度を別の絶対値命令として定義するが、RGB LEDと白色LEDを同時に
混色する専用の公開命令や、各channelの点灯状態を個別確認できるstatus fieldは、現在の
確認範囲では見つかっていない。上記の連続命令後、利用者の目視では白色LEDは点灯して
いなかった。従って、公開APIの`setColorTemperature`をRGB白の後へ送っても、RGB LEDへ
白色LEDを加算する操作にはならない。この観測だけから、機器自体が同時混色できないとは
断定しないが、現在の高速直送経路ではRGBと白色LEDの同時点灯を対応能力として公開しない。
利用者判断により、同時点灯は必要機能から除外した。想定外の消費電力となる可能性もあるため、
専用アプリ、BLE、非公開命令を使った追加探索は行わない。RGBと色温度は排他的な表示方式として
扱い、UIにも同時点灯操作を設けない。

RGB単色を選んだ場合はRGB modeとして扱い、色温度命令を暗黙に追加しない。特に赤色の
実機確認では白色LEDが消灯したままだったため、UIの色指定と色温度指定は排他的なcontrolに
する。
