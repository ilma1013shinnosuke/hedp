# 操作用Adapter 適格性確認計画

## 目的と範囲

Qrioとエコキュートの操作用Adapterについて、共通Execution契約に従って安全性、結果確認、
再送防止、監査可能性を段階的に確認する。本計画は第4層の適格性確認であり、第1層Readerの
確認は[読み取り専用Adapter 実機適格性確認計画](read-only-qualification-plan.md)を正本とする。

本計画を作成しただけでは、実操作、設定変更、常駐化、DB変更、Git操作を許可しない。
各段階は前段階の合格後に進み、実機へ作用する段階では対象、操作内容、影響、停止方法を
示して、その試行に対する明示承認を得る。

## 共通原則

- 第3層は価値を判断してIntentを作り、第4層はIntentを変更せず実行条件を確認する。
- Adapterの書き込み機能を、ExecutionGateを経由せず本番処理から直接呼ばない。
- 送信受付と実状態の成功を分け、`accepted`だけで`completed`にしない。
- timeout、通信断、確認不能は`unknown`とし、成功へ読み替えない。
- Qrioの施錠・解錠、エコキュートの沸き増し等は盲目的に自動再送しない。
- 再起動や再接続後に未完了操作を再生しない。最新状態を読み直してから新しいIntentを扱う。
- 利用者の物理操作と純正アプリ操作を優先し、手動介入後は定義済み期間だけ自動操作を止める。
- 機器自身の凍結防止、安全制御、物理操作、標準機能を妨げない。
- 操作対象は一度に一台、一能力とし、複数対象や自動化へ同時に広げない。
- 認証情報、家庭内address、機器ID、操作先URL、入退室情報をfixture、通常ログ、報告へ出さない。

## 事前条件

実機へ作用する確認の前に、対象Adapterについて次を満たす。

1. 対応するReaderが読み取り専用適格性確認に合格している。
2. 実機が返した能力情報から操作可能項目を確認し、仕様だけから能力を推測していない。
3. `CapabilityDescriptor`にcommand semantics、許容値、確認方法、retry class、timeout上限がある。
4. Intentの期限、対象、能力、権限、現在状態の鮮度と品質をExecutionGateで確認できる。
5. Adapterが返す送信結果と確認結果が共通語彙へ変換できる。
6. timeoutまたは結果不明の後に、書き込みを再送せず読み取りだけで照合できる。
7. 対象の純正アプリ、物理操作、標準安全機能が利用可能である。
8. 試験の開始条件、終了条件、緊急停止方法、復旧確認方法を利用者と共有している。

いずれかを満たせない場合はShadow Modeより先へ進めない。

## 導入段階

### 0. オフライン確認

匿名fixtureと偽Transportだけを使い、ネットワーク通信を発生させない。

- 許容されたcommandだけが、メーカー固有commandへ正確に変換される。
- 未登録能力、未知値、期限切れ、古い状態、低品質状態を送信前に止める。
- 一つのIntentにつき書き込み呼び出しが最大一回である。
- timeout、拒否、通信失敗、曖昧な応答を区別し、秘密を含まない結果を返す。
- 送信後の読み戻しが一致、不一致、利用不能、非対応を区別する。
- 例外本文、`repr`、監査用辞書に秘密値や生の機器識別子を含めない。
- OS、scheduler、DB、Keychain、launchdへ依存せず、同じfixtureがmacOS、Linux、Windowsで
  同じ結果になる。

この段階の結果は実機成功の根拠にはしない。

### 1. Shadow Mode

実際の観測状態と匿名化したIntentをExecutionGateへ渡すが、Adapterの書き込みportは呼ばない。

- `would_dispatch`、`would_block`、`indeterminate`が条件どおりになる。
- Shadowを`accepted`または`completed`として記録しない。
- 重複operation ID、期限切れ、手動操作中、再同期中を止める。
- 監査結果だけから、適用条件と停止理由を説明できる。
- Shadow終了後も実機状態と設定が変化していない。

最低でも正常、拒否、期限切れ、状態欠損、古い状態、手動介入、重複のfixtureを通す。

### 2. 単発の実機確認

試験ごとに明示承認を得て、一台、一能力、一回だけ実行する。承認時に次を提示する。

- 安全な対象別名
- 実現する状態またはtrigger
- 予想される物理的影響
- 実行期限
- 結果確認方法と確認期限
- 結果不明時に自動再送しないこと
- 利用者が物理操作または純正アプリで確認・復旧する方法

送信前に現在状態を取得し、ExecutionGate通過後に一回だけ送る。送信後は書き込みを増やさず、
上限付きの読み取りで状態を確認する。受付、確認、最終結果は別々に記録する。

### 3. 短時間監視

単発確認に合格した能力だけ、操作後の有限監視を行う。監視時間、読取回数、終了時刻には
上限を設け、書き込みは追加しない。

- 受付から実状態反映までの時間
- eventとread-backの一致
- 純正アプリ表示と物理状態の一致
- 遅延反映、順序逆転、重複event
- Reader切断時の`unknown`扱いと再同期
- 手動介入を上書きしないこと
- 家庭LAN、Hub、機器標準制御への影響
- 監査記録と通常ログの容量、秘密情報の非露出

短時間監視の終了後、未完了操作を自動継続しない。

### 4. 半自動運用の審査

単発試験に合格しても、自動化は自動的に許可しない。能力ごとにリスク、利用頻度、
誤作動時の影響、手動復旧、停止時動作を審査する。Qrioの解錠や、給湯の安全・衛生に
関係する操作は、低リスク機能と同じ承認範囲にまとめない。

## Qrioの確認項目

### 初期能力

- `lock`と`unlock`は、いずれも再送禁止の`trigger`として扱う。
- 初期実機試験では、利用者が扉と鍵を直接確認できる状態に限る。
- 解錠は住居の物理セキュリティへ直接作用するため、毎回の明示承認を初期既定とする。
- vendor jobがある場合は、job完了と鍵状態のread-backを分けて確認する。
- 携帯pushだけを実状態確認の正本にしない。取得可能なら鍵状態または履歴eventで照合する。

### 結果の扱い

- command拒否は`rejected`、送信済みか不明なtimeoutは`timeout`または`unknown`とする。
- vendor jobが`pending`、取得不能、形式不明なら`completed`にしない。
- read-backが期待状態と一致したときだけ`matched`とする。
- status取得不能、品質不良、観測時刻不明は`unavailable`とする。
- vendor reference、認証header、lock ID、endpointは通常のreceiptや監査記録へ保存しない。

### Qrioで禁止すること

- timeout、通信断、job未完了、状態不一致を理由にした施錠・解錠の自動再送
- 複数の鍵や複数回操作を一つの試験へまとめること
- 登録・再登録、共有権限、合鍵、ユーザー、Hub、network設定の変更
- 認証済みRaw応答、入退室履歴、家庭固有IDのfixture化または通常ログ保存
- Reader未合格、対象未解決、最新状態不明のままの操作

## エコキュートの確認項目

### 初期能力

- 当該実機の最新property mapでSet可能と確認できたEPCだけを候補にする。
- property mapには対象同一性、観測時刻、鮮度を持たせ、別機器または古いmapを使わない。
- 初期試験は利用者が機器状態と給湯状態を確認できる時間に実施する。
- command受付直後に状態が変わらない可能性を考慮し、上限付きの遅延read-backを使う。
- read-backを増やしてもSet commandは再送しない。

沸き増し、風呂自動、追いだき等の具体的な能力は、規格上の存在だけでは登録しない。
実機のproperty map、値表現、安全条件、停止方法を確認した後に一能力ずつ審査する。

### 結果の扱い

- ECHONET LiteのSet応答は送信受付として記録し、実動作成功とは分ける。
- 対応Getがある場合は期待EDTとの一致を確認する。
- 対応Getがない場合は、能力定義に`not_supported`とその完了条件を明記する。
- 状態反映期限内の一時的不一致は直ちに再送せず、確認継続または`unknown`とする。
- 未知EDT、長さ不正、別transaction、別object、別EPCの応答を成功にしない。

### エコキュートで禁止すること

- property map未確認、古いmap、別対象のmapによるSet
- timeout、通信断、確認不能、反映遅延を理由にしたSetの自動再送
- 凍結防止、衛生、安全制御を止める操作
- network、登録、時刻、firmware、保守設定の変更
- 複数EPCを一括変更する初期試験
- 実通信Raw、家庭内address、機器ID、設定値を通常ログやfixtureへ複製すること
- 利用者の手動操作中、純正アプリ操作中、機器再同期中の操作

## 合格基準

Stage 1以降へ進む前に、共通`Intent`、`CapabilityDescriptor`、`ExecutionGate`、
追記型監査、再起動時の未完了操作の扱いが実装され、Adapterを直接呼べないことを
契約試験で固定する。機器・能力ごとの確認期限、read-back回数上限、停止条件、
必要成功回数も付表で確定する。現在のQrio・エコキュート操作AdapterはStage 0の
オフライン部品であり、この前提を満たすまでは実機へ送信しない。

能力ごとに次をすべて満たした場合だけ、その段階を合格とする。

- 未許可、期限切れ、重複、状態不鮮明なIntentが送信前に停止する。
- 一Intentにつき書き込み試行が最大一回で、結果不明後に再送しない。
- `DispatchReceipt`と`VerificationResult`を分離し、受付だけを成功扱いしない。
- 一致、不一致、拒否、timeout、通信失敗、確認不能を正しく区別できる。
- 再起動または再接続後に古いIntentを送信しない。
- 手動介入を検知または申告した場合、定義済み期間だけ操作を停止する。
- 実機、純正アプリ、物理状態の間に説明不能な不一致が残らない。
- 機器標準機能、安全機能、家庭LAN、他Adapterへ悪影響を与えない。
- 秘密値と家庭固有情報がfixture、通常ログ、例外、監査要約、報告へ出ない。
- 同じ匿名fixtureと共通契約testがmacOS、Linux、Windowsで同じ結果になる。
- 停止、結果不明、手動復旧の手順を利用者が理解できる。

一項目でも満たさなければ不合格とし、自動で操作回数、timeout、再試行、対象範囲を増やさない。

## OS非依存性

Adapterのprotocol変換、結果型、ExecutionGate、fixture testは純粋なPythonとして実装し、
macOS固有のKeychain、launchd、GUI automation、絶対pathへ依存させない。秘密情報の注入、
scheduler、service管理は実行環境側の責任とする。

確認対象は次のとおり。

- socketとHTTPSの標準的なAPIだけをAdapter境界で使用する。
- path区切り、timezone、文字encoding、signal、process管理をOS既定へ依存させない。
- Linuxではsystemd、Windowsではサービス管理機構を別の運用層として扱う。
- OSが変わっても安全な別名、Intent、receipt、verification、outcomeの意味を変えない。
- OS固有機能が必要になった場合はAdapterへ混在させず、交換可能なportとして分離する。

## 本番化との境界

本計画への合格は、本番常駐化、自動判断、DB migration、認証情報移行を意味しない。
それらは個別に、容量、backup、監査保存期間、停止方法、LinuxまたはWindowsのservice定義、
復元方法を確認して承認を得る。

操作Adapterは本番接続前にReaderと別の公開interfaceを維持し、収集serviceへ書き込み機能を
混在させない。最初の本番化後も、機器追加、firmware更新、API変更、property map変更時には、
オフライン確認から該当能力の適格性を再確認する。
