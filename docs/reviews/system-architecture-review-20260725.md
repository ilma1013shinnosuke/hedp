## 重要度付きの改善候補

### P1 — 実機操作を導入する前に④の最小縦切りを固定する

**確認済み事実:** ④は詳細な安全契約を持つが、本番コード、CapabilityDescriptor、Intent、ExecutionGate、監査表は存在しない。Adapterには読み取り中心の実装があり、少なくともModbus TCPはread-onlyである。

**リスク:** 最初の書込みをAdapterやCLIへ直接追加すると、承認、期限、状態鮮度、重複抑止、結果不明、手動操作との競合が経路ごとにばらつく。

**提案:** 最初の低リスク・単一対象・絶対状態指定だけを対象に、`Intent → Gate → adapter dispatch → read-back → audit`をShadow Modeで通す。高リスクの鍵・火気・給湯・空調はこの受入条件を満たすまで対象外にする。

**受入条件:**

- Adapterを直接呼ぶ本番自動化経路がないことをtestで固定する。
- `expired`、`blocked`、`unavailable`、`unknown`、`partial`を含むfixture testがあること。
- 再起動後に未完了操作を送らず、読み戻し不能なら再送しないこと。
- 操作ごとにcontrol owner、手動解除、停止時動作、確認方式、期限が記録されること。

### P1 — 共有lockによる欠損を測定し、取得と書込みの分離を判断する

**確認済み事実:** 日次ジョブは長い一連の作業中に共有lockを持ち、5分・毎時・日次健全性ジョブはlock取得失敗時に正常終了としてskipする。ADR 001も見送り回数の健全性確認を今後事項としている。

**推測:** クラウド遅延、補完、backupのいずれかが長引くと、独立機器の観測欠損が増える可能性がある。実際の頻度と継続時間はDB・launchd・ログ未確認のため未確定である。

**提案:** まずlock保持時間、skip数、取得元別の欠損、transaction時間を値なしの運用指標として記録する。実測で閾値を超えた場合のみ、取得（外部I/O）と短いDB反映の分離、又は取得元別queueを比較する。

**受入条件:**

- skipが「成功」に見えず、日次健全性で件数・原因・影響時間が分かること。
- 一取得元のtimeoutで他取得元の予定遅延が合意した上限内であること。
- 同じSQLiteへの同時書込みを再導入しないこと。

### P2 — ③の初回実装はルールエンジンではなく一つの判断に制限する

**確認済み事実:** ③の設計は安全、快適性、経済性、鮮度、予測、通知、ユーザー訂正、系列管理を扱うため、設計面は意図的に広い。一方、ADR 003は最初の実装を一つの低リスク判断、匿名fixture、Shadow Modeに限定している。

**リスク:** 設計全体を先に汎用ルールエンジンとして実装すると、判断根拠・期限・優先順位・通知抑制をテストできない抽象化になる。

**提案:** 最初のユースケースを「情報表示または提案」に留め、入力データの品質・鮮度、判断しない条件、系列上限、説明文まで一つのfixture群で固定する。

**受入条件:** 判断しないケースが正常ケースと同数程度のtestで明示され、通知や操作が発生しないことを検証できること。複数機器最適化、学習、恒久的好み推定は対象外とする。

### P2 — 集約点の分割はCLI・workflow単位で段階的に行う

**確認済み事実:** `main.py`と`application.py`は各約840行で、CLI組立て、依存構築、workflowが集約されている。現行文書も即時の大規模抽象化を避ける方針である。

**提案:** 新規機能に触れるタイミングで、CLI parser、依存構築、FusionSolar workflow、SwitchBot workflow、品質workflowを移す。振る舞いを変えない移動ごとに既存CLI testを残す。

**受入条件:** `main.py`は入口・引数解釈・終了コードに限定され、各workflowが単独でfixture testできる。DB schema・実データの変更を伴わない。

### P2 — 移行中の`hedp`名称を期限付き互換として管理する

**確認済み事実:** `HEDP_`/`SUMICORE_`、旧新CLI、launchd label、path、lockが併存し、文書は段階移行を明示している。

**推測:** 互換の終了条件が未確定のまま新規機能を増やすと、設定・ログ・運用手順の二重化が恒久化する恐れがある。

**提案:** runtimeを変更しない範囲で、各互換項目に「移行前提」「観測方法」「終了判断日」を対応表として追加する。実際の切替は収集の安定期間とrollback条件を満たした別作業で扱う。

**受入条件:** 新規設定・新規文書は原則`SUMICORE_`/SumiCoreを正とし、旧名を使う箇所は互換理由と削除条件を追跡できる。

### P3 — 未配備・監視中の経路を現役経路と混同させない

**確認済み事実:** FusionSolarのGAS受け渡しは未配備、Modbusは監視中であり、`parallel`が既定である。`docs/current-layout.md`と`docs/system-review.md`には状態が記録されている。

**提案:** READMEの運用導線で「現役」「監視中」「未配備」を短い表で示し、各経路の目的、責任者、切替条件、停止条件を一か所へ集約する。

**受入条件:** 新しい運用者が、既定で実行される経路と実験・移行経路をコードを読まずに区別できる。

## 明確な非問題・保留

- ③④が未実装であること自体は欠陥ではない。文書は早期の汎用化を禁じ、低リスクの段階導入を要求している。
- つむのindex検査では境界違反・操作ループ危険は検出されなかった。ただしこれは実行時の実機状態、実スケジュール、実データの競合を証明しない。
- 機器自立性は文書契約として確認できた。個々の機器の物理操作、純正アプリ、停止時挙動は実機確認をしていないため、機種別の保証とはしない。

## 推奨順序

1. P1の「④の最小縦切り」の受入条件を先にtest仕様へ落とす（実機操作はしない）。
2. P1のlock/skipをread-only観測し、実測後に収集分離の要否を決める。
3. P2の最初の③ユースケースを提案・Shadow Modeとして設計し、④の受入条件を再利用する。
4. 上記に触れる変更に合わせてP2のworkflow分割と互換期限の記録を行う。

この順序なら、データ保存・収集の既存運用を壊さずに、将来の判断・操作を安全に追加する土台を先に検証できる。
