# SumiCore全体レビュー

## 目的

機能追加を続ける前に、実運用で生じた容量、失敗対応、保守負担、複雑性を見直し、
SumiCoreの思想に沿って小さく安定した基盤へ整える。本書は問題を隠さず、対応順と
完了条件を共有するための現行レビューである。

## 確認範囲

- Git管理中の設計文書、ADR、運用手順、Adapter資料
- Python package、shell script、GAS試作、test
- SQLiteのSchema、テーブル別容量、件数、期間、Raw重複
- launchdの現行・旧plist、実行間隔、ログの増加
- 仮想環境、build生成物、backup、空き容量

秘密値、家庭固有ID、Raw本文はレビュー記録へ複製していない。実API、実機、DB、backupの
内容変更も行っていない。

## 維持する強み

- 収集、蓄積、判断、実行の責任境界が明確になっている。
- メーカー固有処理がAdapter内に隔離されている。
- 読み取り機能と操作機能を公開面・実行経路ともに分離する方針がある。
- Raw、正規化値、品質、欠損を区別し、推測を事実として扱わない。
- Modbus TCPは読み取り機能だけを実装し、書き込みfunctionを拒否する。
- backupは途中ファイル、空き容量、mode、失敗時の旧世代保持を考慮している。
- 自動testが主要な収集、保存、品質、切替処理を覆っている。

## 最優先

### 1. SwitchBot履歴を現役DBから分離する

現役DB容量の大部分は過去CSVから取り込んだSwitchBot観測と二つの索引である。Raw本文だけ
でなく、秒精度の正規化行を現役SQLiteへ置き続ける構造が容量を増やしている。

2026-07-25時点の読取専用集計では、過去CSV由来は29か月、9,067,009件である。
月別件数は9,502〜491,040件、Raw本文の合計は約1,580 MiBである。月ごとの件数差が
大きいため、保存容量は「一定件数/月」ではなく実測値と上限の両方で監視する。

過去履歴を可逆JSON Lines gzipへ移し、長期集計と重要イベントだけを現役DBへ残す。
移行は旧DBを直接削る方式ではなく、新しい小型DBを検証してから原子的に切り替える方式を
優先する。元DBの削除は別承認とする。

### 2. backupを別障害領域へ複製する

圧縮backupが同じMacに一世代だけでは、故障、盗難、ファイルシステム障害へ備えられない。
Raw削減前に、暗号化した正常backupまたはアーカイブを別媒体かクラウドへ置き、
checksumと復元手順を確認する。

### 3. Modbusと旧クラウド経路を分離する

現行のリアルタイムジョブは、ローカルModbus取得後に旧クラウドAPIも順番に試す。
クラウド認証やCAPTCHAの失敗が、ローカル取得の実行時間、共通DB lock、ログ量へ影響する。
24時間確認完了後はModbusを独立した主経路にし、旧経路は頻度と目的を限定する。

## 高優先

### 保存方針を実装へ接続する

共通保存方針は文書化したが、Adapterごとの保存クラス、日次上限、保持期間、集約、
アーカイブ、削除ゲートはまだコードと設定へ接続されていない。新規Adapterはこの情報が
ないまま無制限の本番保存を始めない。

### SwitchBotの同一応答二重保存を止める

成功したstatus応答が観測行と収集イベントの両方に保存される。観測行を応答本文の正本、
収集イベントを成否・遅延・error種別の証跡とし、成功時のRaw本文をイベントへ複製しない。
失敗本文も秘密情報を除いた上限付き診断情報だけにする。

この変更はsourceとtestへ実装済みだが、現行`.venv`へは未展開である。既存行は変更しない。

### 収集ジョブの障害範囲を狭める

現在は複数の独立収集が一つのディレクトリlockを共有する。書き込み競合は避けられるが、
遅いクラウド処理がローカル収集やSwitchBotをskipさせる。取得とDB反映を分ける、
短い書き込みtransactionにする、または取得元別queueを使う案を、実測後に選ぶ。

### ログを上限付きにする

SwitchBotだけに簡易rotationがあり、他ジョブは無制限である。全ジョブで同じ容量上限、
世代数、mode 0600、秘密値redactionを適用する。毎回同じ既知警告を出さず、連続失敗は
最初・状態変化・定期要約だけを記録する。

5 MiB、二世代、mode 0600のrotationと、新規出力に家庭固有IDを含めない変更は実装済みで
ある。既存の過去logは監視・診断が終わるまで自動削除せず、別承認で扱う。

### 十年運用向けの検索構造へ進める

共通RawDataとRecordはJSON TEXT一列で、多くの検索が`json_extract`または全件読込である。
現状件数では動くが、十年分では健全性確認と再計算が重くなる。既存JSONを正本として保ちつつ、
source、timestamp、target_dateの生成列または索引を段階追加する。

## 中優先

- `main.py`と`application.py`がCLI、構築、workflowを集めて大きいため、機能追加時に
  command単位で分離する。今すぐ抽象基盤だけを作らない。
- launchd installerに重複が多く、uninstallerが全現行jobを対象にしていない。共通生成処理と
  job定義を一か所へまとめる。
- 秘密情報をplistへ平文展開する現方式は、mode 0600でも将来の秘密保管方針と一致しない。
  セキュリティレビューでOS非依存の暗号化正本と実行時注入へ移す。
- private handover文書は解決済み事項を未決として残している。現行設計へのリンクと
  「現在の差分」を更新し、過去経緯と現行仕様を区別する。
- GAS版FusionSolarは未配備である。Modbusで代替できない日次・履歴データの必要性を確認し、
  必要なら限定配備、不要なら知識文書だけ残して現役コードから外す。
- 名称移行はpackage互換性を優先して途中状態にある。機能が安定するまで強制改名を進めず、
  外部互換期限を決めてから行う。

## 容量の小さい整理候補

次は現役DBやRawとは別で、参照がないことを最終確認した後に削除できる。

- 失敗したPython仮想環境
- 切替前の旧Python仮想環境
- package build生成物
- IDE cache
- 未loadの旧launchd plist

これらは再生成可能だが、旧環境は切替監視とrollback期限が完了するまで残す。

## 文書レビュー

設計文書間に壊れたlocal linkと完全重複段落はない。役割は次のように維持する。

- `PROJECT.md`: 目的、役割、長期原則
- `SPECIFICATION.md`: 現行の技術仕様
- `docs/01`〜`04`: 四層の責任
- `docs/execution-contract.md`: 第4層の詳細契約
- `docs/adapter-lifecycle.md`: 新規機器の調査から廃止まで
- `docs/decisions/`: 採用理由と変更時の判断材料
- `docs/integrations/`: メーカー別の確認済み知識
- 運用runbook: 人が実行する具体的手順

切替runbookと監視文書は監視完了後に履歴扱いとし、READMEの主要導線から外す。過去経緯は
Git履歴で保持し、同じコードや文書を別archiveへ複製しない。

## 実施順

1. Modbus 24時間監視を完了し、旧リアルタイム経路を分離する。
2. 保存クラスと復元可能なアーカイブ形式をtestで固定する。形式と検証器は実装済み。
3. 暗号化した別障害領域の複製を確保する。
4. SwitchBot過去履歴でarchive・restore・小型DB再構築をdry-runする。実DBを変更しない
   月次archiverと小型DB builderは実装済みで、実データ生成は保存先確定と承認を待つ。
5. 対象、件数、容量、影響を提示し、実データ切替の承認を得る。
6. ログ上限、収集分離、索引、installer整理を順に実装する。ログ上限とModbus単独modeは
   sourceへ実装済みで、本番切替は未実施。
7. security reviewを実施し、秘密保管、権限、ネットワーク、backupを修正する。
   初回reviewと安全な`.env`読込は完了し、暗号化した別障害領域backupは未完了。

## 2026-07-26 操作Adapter進捗

Qrioとエコキュートは、読み取り経路と分離した操作専用Adapterを追加し、匿名fixtureによる
オフライン検証まで完了した。いずれも一つの依頼につき書き込みは最大一回であり、timeout、
通信異常、結果確認不能では操作を自動再送しない。送信受付と状態確認を分離し、一致を確認
できない結果を成功へ変換しない。

Qrioは、家庭固有のlock IDをRequest、Receipt、通常ログへ渡さず、秘密IDを閉じ込めた
read-back callableを注入する。vendor job参照も公開結果へ残さず、必要な確認中だけメモリ内で
使用する。エコキュートは、対象、観測時刻、有効期限を持つ実機由来property mapだけを許可し、
別機器、期限切れ、未確認EPCを送信前に遮断する。現在の最小実装では0〜30秒の待機後に
一度だけread-backし、Set command自体は再送しない。

全体回帰試験は607件成功した。これは実機適格性や本番利用の承認を意味しない。次段階は
[`operation-qualification-plan.md`](integrations/operation-qualification-plan.md)に従い、
Readerの実機適格性、Shadow Mode、対象・操作・回数を限定した単発試験の順で進める。
実機、現役DB、launchd、認証設定、Gitはこの実装作業では変更していない。

## 完了条件

- 通常運用で同じ失敗通知の対応を繰り返さない。
- 一つの取得元の失敗が他の取得を止めない。
- 月次のDB・archive・log増加量を説明し、上限を持つ。
- 任意のarchiveをchecksum付きで復元し、件数と内容一致を確認できる。
- SumiCore停止中も家の標準機能が継続する。
- 新規Adapterが統一手順と保存上限なしに本番へ入らない。
- 秘密値と家庭固有IDがGit、通常log、回答へ出ない。
