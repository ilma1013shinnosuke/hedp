# SumiCore 共通Execution層 基本設計

## 1. 目的

Execution層は、③情報利用・判断層や利用者が作った「何を実現したいか」を受け取り、
対象機器に合った命令へ変換し、安全に実行して結果を確認する。

この層が共通化するのは、メーカーの通信方式ではなく、次の事項である。

- 誰が、何を、なぜ依頼したか
- その操作を今実行してよいか
- どの機器へ、どの命令を送ったか
- 命令が受け付けられたか
- 実際の状態が期待どおりになったか
- 失敗、結果不明、一部成功をどう扱ったか
- 手動操作、再起動、通信断が起きたときにどう止まるか

## 2. 4層の中での位置

```text
① 情報収集 ──> ② 情報蓄積 ──> ③ 情報利用・判断
       ^                                  │
       │                                  │ 操作意図
       │                                  v
       └──── 状態確認 <────────── ④ 操作・実行
                                             │
                                             v
                                       メーカー別Adapter
                                             │
                                             v
                                           実機
```

- ①は機器の状態と出来事を取得する。
- ②はRawData、正規化値、履歴、イベントを保存する。
- ③は事実を使って価値を判断し、メーカーに依存しない操作意図を作る。
- ④は許可済みの操作意図について実行条件を検査し、具体的な命令を送り、状態を確認して
  監査記録を残す。

読み取り専用の定期収集は①の責任であり、④を経由させない。④が状態確認に使う読み取りは、
各Adapterが提供する同じ読み取り機能を再利用できる。

## 3. 基本原則

### 3.1 機器の自律を基本とする

SumiCoreは機器を置き換える必須制御装置ではなく、連携と拡張を担当する。SumiCoreが
停止しても、機器自身の安全機能、物理操作、純正アプリ、標準スケジュールは原則として
継続できる構成にする。

SumiCoreを管理主体にすることは禁止しない。ただし、採用理由、得られる利益、停止時動作、
手動解除、操作期限、結果確認方法を機能ごとに明記する。機器の安全機能をSumiCoreだけに
移すことは認めない。

### 3.2 「送信」と「成功」を分ける

メーカーから受付応答を得ても、実機が期待状態になったとは限らない。そのため、
命令を送った事実と、読み戻しなどで確認した結果を別に記録する。

### 3.3 不明を成功にしない

タイムアウト、通信断、確認不能は成功として扱わない。送信済みかどうかも判定できない
場合は `unknown` とし、危険な再送を避ける。

### 3.4 古い命令を再生しない

再起動や再接続の後に、保存済みの状態や未完了命令を自動再送しない。まず現在状態を
取得し、鮮度と品質を確認してから新しい操作を受け付ける。

### 3.5 小さく導入する

可視化、提案、Shadow Mode、半自動、低リスク自動化、高リスク操作の順に進める。
将来必要そうという理由だけで、汎用ワークフロー、分散トランザクション、自動ロールバック
などを先に実装しない。

## 4. 責任分界

### 4.1 Execution層が担当するもの

- 操作意図の形式検査、期限確認、対象解決
- 能力、権限、安全上の実行条件、管理主体の確認
- 重複抑止、同時実行制御、上限付き再試行
- 単一・複数対象の実行計画
- Adapterへの命令送信
- 受付結果と実状態の確認
- 手動操作を検知した場合の一時停止
- 操作と判断理由の監査記録

### 4.2 Adapterが担当するもの

- メーカー固有の認証、通信、コマンド変換
- メーカー固有エラーの共通分類への変換
- 命令送信と受付応答の返却
- 状態確認に使える読み取り機能

Adapterは利用者権限、家庭全体の価値判断、複数機器の順序、無制限な再試行を担当しない。
既存Adapterの書き込みメソッドを、共通検査を通さず本番自動化から直接呼び出さない。

### 4.3 ③情報利用・判断層が担当するもの

- どの事実から、なぜ操作が必要と判断したか
- 期待する家庭内の状態
- 判断の確信度、規則・モデルの版
- 情報表示、利用者への提案、事前承認範囲での自動操作のどれにするか
- 経済性、快適性、健康性、安全性、機器保護などを比較した結果

③はメーカー固有コマンド、認証情報、通信上の再試行方法を知らない。

## 5. 最小の共通契約

### 5.1 CapabilityDescriptor：できることの説明

機器やAdapterが提供できる操作を登録する。

| 項目 | 意味 |
|---|---|
| `capability` | `light.power.set`などの共通名 |
| `target_type` | 照明、鍵、テレビ、給湯器など |
| `command_semantics` | `state_set`、`relative`、`trigger`、`configuration` |
| `parameters` | 許される値、範囲、単位 |
| `verification` | 読み戻し、イベント確認、受付のみなど |
| `retry_class` | `safe`、`reconcile_then_retry`、`never_auto` |
| `default_timeout` | 機器・通信方式ごとの上限 |

リスク区分と必要な確認条件は、能力と対象ごとの設定として事前に定義する。依頼者が
Intentによってリスク区分を下げることはできず、ExecutionGateは定義済み条件を検査する。

### 5.2 Intent：操作意図

「どのメーカー命令を送るか」ではなく「家庭内で何を実現したいか」を表す、変更しない依頼書
である。

| 項目 | 意味 |
|---|---|
| `operation_id` | 操作全体を追跡する一意な識別子 |
| `requested_at` | 依頼を受けた時刻 |
| `expires_at` | この時刻を過ぎたら実行しない |
| `requester` | 利用者、規則、外部イベントなど |
| `reason` | 判断理由または利用者の目的 |
| `target` | 安全な機器別名、部屋、グループ |
| `capability` | 実現したい共通操作 |
| `desired_state` | 期待状態または操作パラメータ |
| `priority` | 衝突時の比較に使う優先度 |
| `control_owner` | 機器、SumiCore、利用者の管理主体 |
| `correlation_id` | 関連する判断・外部イベントとの対応 |

`operation_id`はSumiCore内の重複抑止と追跡に使う。メーカー側が同じ識別子による
冪等性を保証するとは仮定しない。

### 5.3 ExecutionGate：実行条件確認

ExecutionGateは価値判断を行わず、③が決めたIntentを変更したり、より良い代案を選んだり
しない。実行直前に、Intentが許可された条件を満たしているかだけを検査する。

- `pass`: 実行条件を満たしている
- `blocked`: 権限、事前承認、安全上の制限、現在の利用者指定などにより実行できない
- `expired`: Intentの期限が切れている
- `unavailable`: 現在状態、接続、能力などを確認できず実行できない

検査対象は、対象と能力の存在、権限、事前承認範囲、期限、現在状態の鮮度と品質、
重複、機器の許容範囲、現在の利用者指定との整合である。経済性、快適性、健康性の比較や、
自動操作にするか利用者へ提案するかの選択は③が担当する。

結果には、適用した実行条件、通過または停止した理由、確認した状態の時刻と品質を残す。
`blocked`、`expired`、`unavailable`の場合は操作内容を作り替えず、結果を③へ返す。

能力が取り得る値は、電源のような列挙値なら許可値を完全一致で登録する。温度、音量、
充放電量のような範囲値は、能力ごとに型と上下限を検査する純粋なvalidatorを登録する。
列挙値にもvalidatorにも合格しない値、またはvalidator自身が失敗した場合は
`desired_state_invalid`として送信前に停止する。Adapter内で値を丸めたり、安全そうな
値へ置き換えたりしてはならない。

### 5.4 DispatchReceipt：送信の記録

Adapterへ何を送り、通信上どう見えたかを表す。

- 送信を試みた時刻
- Adapterと経路
- 対象の安全な別名
- 試行番号
- `accepted`、`rejected`、`timeout`、`transport_error`、`unknown`
- メーカー応答の秘密情報を除いた要約

これは実機の成功結果ではない。

### 5.5 VerificationResult：実状態の確認

- 期待状態
- 観測状態
- 観測時刻、鮮度、品質
- 確認方法
- `matched`、`not_matched`、`unavailable`、`not_supported`

確認できない機器では、受付応答だけで完了とする能力なのか、結果不明とするのかを
CapabilityDescriptorに明記する。

## 6. 進行段階と最終結果

「今どこまで進んだか」と「最終的にどうだったか」を混ぜない。

### 6.1 Phase：処理の進行段階

`received` → `gate_checking` → `ready` → `dispatching` → `verifying` → `finished`

### 6.2 Outcome：最終結果

| 結果 | 意味 |
|---|---|
| `completed` | 期待状態を確認できた |
| `failed` | 拒否、明確な失敗、期待状態との不一致 |
| `unknown` | 送信または実状態を確認できない |
| `partial` | 複数対象の一部だけ完了した |
| `skipped` | すでに期待状態、または実行不要 |
| `cancelled` | 利用者または上位処理が取り消した |
| `expired` | 実行前または途中で期限を過ぎた |

Shadow Modeでは実機へ送信せず、`would_dispatch`、`would_block`、
`indeterminate`を評価結果として残す。Shadowを`completed`とは記録しない。

最初のShadow専用実装は`src/hedp/operations/shadow_execution.py`に置く。共通Gateと
単発送信のオフライン検証は`src/hedp/operations/execution.py`、メーカー別の薄い接続は
`src/hedp/operations/adapter_ports.py`に置く。後者も匿名fixtureだけで検証し、CLI、
現役DB、定期job、実機へは接続しない。

process-local registryは同一process内の重複dispatchを原子的に止めるためのものであり、
再起動後の冪等性や未完了操作の再開を保証しない。Adapterが例外を返した場合も同じIntentを
自動再送せず`unknown`とする。Shadow評価はdispatchではないためoperation IDを消費しない。
承認は対象と能力だけでなく、operation ID、requester、具体的なdesired stateへ結び付け、
別操作へ流用できないようにする。実行モードは明示した`fixture`だけを送信可能とし、不明な
値は必ず停止する。`fixture`で呼べるPortは、匿名fixture用として型・実装上明示されたもの
だけとし、任意の実transportを注入して送信できないようにする。状態証拠も対象別名と能力へ
結び付け、別機器・別能力の状態を流用しない。Adapterの結果が受付・確認・最終結果の間で
矛盾する場合は`unknown`として扱う。永続registryを導入するまでは、本番経路を有効にしない。

## 7. タイムアウトと再試行

共通化するのは秒数ではなく、必ず上限を持つという原則である。秒数、回数、待機間隔、
総実行時間は機器・能力・通信経路ごとに設定する。

| 操作種別 | 例 | 再試行方針 |
|---|---|---|
| 読み取り | 現在状態取得 | 短時間・上限付きで再試行可能 |
| `state_set` | 照明を消灯、音量を20へ | 現状態を再取得し、未達の場合だけ再試行候補 |
| `relative` | 音量を1上げる | 結果確認なしの自動再送を避ける |
| `trigger` | 解錠、追いだき開始、Wake-on-LAN | 原則として盲目的に再送しない |
| `configuration` | スケジュール、ネットワーク設定 | 明示確認を要し、自動再試行しない |

失敗回数、理由、待機時間、最終的な扱いを記録する。時間切れを成功扱いしない。

## 8. 単一対象と複数対象

単一機器の操作を基本単位とする。部屋、シーン、家庭全体など複数対象の操作は、
親Operationと子Operationに分ける。

- 子ごとにExecutionGate、送信、確認、結果を持つ。
- 親は子の結果を集約し、全完了、一部成功、全失敗を表す。
- 一台の失敗で、確認済みの他機器まで失敗扱いにしない。
- メーカーやGatewayをまたぐ原子的な一括成功は保証しない。
- 安全な補償操作が明示されていない限り、自動ロールバックしない。

## 9. 手動操作と競合

利用者の物理操作や純正アプリ操作を、通常はSumiCoreの自動制御より優先する。

- 操作元を特定できる場合は `manual_override` として記録する。
- 定期取得で差だけを見つけ、操作元を特定できない場合は `external_change` とする。
- 手動操作後は、対象×能力ごとのクールダウン期間中、自動操作を抑止する。
- 同じ機能を機器側とSumiCore側の両方でスケジュールしない。
- 同じ対象・能力に対する新しい利用者指定は現在の指定内容を更新する。③が作るIntentは
  その現在指定と整合させ、④は実行直前に整合を確認する。

## 10. 起動、再接続、障害時

AdapterまたはGatewayごとに `syncing` 状態を持つ。次の条件がそろうまで新しい命令を
送らない。

1. 接続先と対象機器を確認できた。
2. 現在状態を読み取れた。
3. 状態の鮮度と品質が操作条件を満たした。
4. 未完了Operationを再送せず、`unknown`など適切な結果へ整理した。

Execution層の停止は①収集、②蓄積、③分析を壊さない。Adapter障害は他メーカーの
Adapterへ波及させない。実行端末、家庭LAN、クラウドが停止した場合の挙動を能力ごとに
定義する。

## 11. 監査と保存

操作履歴はRawDataや通常の観測Recordとは目的が異なるため、将来の実装では専用の
追記型台帳を使う。最小候補は次の3表である。

- `execution_operations`: Intent、Phase、Outcome、ExecutionGate結果、親子関係
- `execution_attempts`: 各送信試行、DispatchReceipt、VerificationResult
- `execution_audit_events`: 確認、取消、手動介入、状態遷移、例外

現時点ではDB変更を行わない。最初の本番操作機能を実装するときに、バックアップ、
容量、既存DBとの互換性を確認してからMigrationを設計する。

監査記録は、操作意図、③の判断理由、対象、実行者、適用した実行条件、送信、確認、最終結果を
後から説明できなければならない。パスワード、Token、Cookie、秘密鍵、家庭固有の
生の識別子は保存・表示しない。必要な認証情報は安全な参照名だけを持つ。

## 12. 機器別の初期方針

| 対象 | 初期方針 |
|---|---|
| Smart LEDZ | 読み取り確認から始め、Shadow後に単一照明の絶対指定を候補とする |
| SwitchBot照明 | 絶対状態の確認を優先し、複数命令の原子性を仮定しない |
| BRAVIA | 電源・音量など読み戻せる絶対指定を優先し、Wakeは確認できるまで送信扱い |
| Qrio | 解錠を高リスクTriggerとして扱い、盲目的に再送しない |
| エコキュート | 風呂自動・追いだき等を高リスクTriggerとして扱い、機器標準機能を優先する |
| FusionSolar Modbus | 読み取り専用の①情報収集であり、現時点のExecution対象外 |

この表は能力の確定ではない。公開仕様と実機検証で確認できた機能だけを登録する。

## 13. 導入手順

1. 本設計、匿名fixture、状態遷移テストを作る。
2. 最初のAdapterで読み取りと能力表を確認する。
3. Shadow ModeでExecutionGate、対象解決、監査記録だけを検証する。
4. 明示承認の下、低リスク・単一対象・絶対指定を試験する。
5. 実状態の読み戻しと障害時挙動を検証する。
6. 複数Gateway・複数対象へ広げる。
7. 半自動運用を経て、低リスク機能だけを自動化する。
8. 鍵、給湯、設定変更など高リスク機能は個別審査する。

段階を進める条件は、重複抑止、期限切れ、通信断、結果不明、再起動、手動介入、
一部失敗をテストでき、監査記録から経緯を説明できることである。

## 14. 現時点で決めないこと

- DBの最終Schemaと保存期間
- 認証・認可の具体的な実装方式
- UIや音声操作の形式
- 全メーカー共通の固定タイムアウト秒数
- 汎用ワークフローエンジン
- 複数メーカーをまたぐ自動ロールバック

これらは最初の具体的な利用要件と実機検証を得てから、必要な範囲だけ決める。
