# HESTIA v1.0 正式リリース・ロードマップ

## 文書の位置づけ

本書は、HESTIA（Home Energy & Smart Technology Intelligent Assistant）を、
安全に日常利用できるv1.0へ進めるための正式な実行順序を定める。
個々の作業の合否は
[v1.0リリース・チェックシート](hestia-v1-checklist.md)へ記録する。

既存の思想、四層構造、Adapter追加手順、保存方針、実機適格性確認を置き換えず、
それらを一つのリリース判定へ束ねる。コードが存在すること、オフラインテストが通ること、
実機で適格性が確認されたこと、本番常駐していることを区別する。

## v1.0の到達点

v1.0は、家庭の必須制御装置ではなく、機器の標準機能を尊重する非必須の補助知性として、
次を満たす状態とする。

1. 許可された機器から、品質・鮮度・欠損を区別して状態とイベントを収集できる。
2. Raw、正規化値、現在状態、状態区間、イベント、観測可能期間を区別して保存できる。
3. 限定された判断について、入力、根拠、判断しない理由を説明できる。
4. 許可済みIntentだけをExecutionGateで検査し、実行受付と結果確認を分けられる。
5. HESTIA、KURA、クラウド、ネットワークのいずれかが停止しても、機器自身の安全機能、
   物理操作、純正アプリ、機器内スケジュールを妨げない。
6. 容量、バックアップ、秘密情報、通知、障害対応が、利用者へ過度な管理負担を生まない。
7. v1.0はmacOSを保証対象として運用し、主要な契約とAdapterは将来LinuxまたはWindowsへ
   再適格化できる境界を保つ。

v1.0は「接続候補の全機能を自動操作できること」を意味しない。未適格の機器や能力は、
明示的に`fixture_only`、`reader_only`、`shadow_only`または`deferred`として残せる。

## v1.0の保証対象OS

- 正式な保証対象はmacOSとする。
- LinuxとWindowsはv1.0のリリース必須条件に含めず、移行先が確定した時点で再適格化する。
- core、共通契約、AdapterをOS固有serviceから分離する設計条件は維持する。
- launchdはmacOS配備Adapterとして扱い、coreの契約へ混在させない。
- LinuxまたはWindowsへ移す際は、共通fixture、秘密注入、service管理、保存先、復元、
  ネットワーク権限を対象OS上で再試験する。
- 未試験のOSで動作することをv1.0の保証や実績として表示しない。

## v1.0の承認済み最小保証範囲

2026-07-28の利用者承認により、v1.0の本番候補能力は、macOS上で動作する
FusionSolar / SmartLoggerの既知Modbusレジスタによるread-only収集だけとする。
本番昇格には、単発・短時間・24時間の匿名化済み適格性証拠、取得周期と容量上限、
監視、停止、復旧、rollbackの確認が必要である。

他Integrationの読み取り、自動判断、および発電停止、蓄電池充放電、照明、給湯、鍵、
家電、テレビ、車両を含む全実機操作はv1.0の保証対象外とする。実装やfixtureは削除せず、
`fixture_only`、`reader_only`、`shadow_only`または`deferred`として次版へ維持する。

## KURAとの関係

### 採用方針

HESTIAは将来KURAと接続できる境界をv1.0で確定するが、KURAをv1.0の必須依存にはしない。

KURAへ任せられるのは、情報源からRawを取得し、要求元へ配達し、保存可能なRawだけを
可逆圧縮して保管する責任である。HESTIAは、取得目的、必要な鮮度、Raw境界、失敗時動作、
正規化Schema、保存規則、判断、操作を引き続き所有する。

```text
情報源
  ├─ 現行HESTIA Collector ─┐
  └─ 将来KURA Connector ──┼─ Raw受渡契約 ─ HESTIA第1層
                           │
                           └─ 公開可能Rawの可逆保管

HESTIA第1層 → 第2層 → 第3層 → 第4層
       └─ 即時イベント経路はKURAの完了を待たない
```

### v1.0で固定するKURA接続境界

- 依頼には、情報源alias、目的、許可domain、頻度、鮮度、Raw単位、容量上限、
  timeout、retry、停止条件を含める。
- 配達物には、内容hash、取得時刻、資料時点、source、Schema識別、品質を含める。
- 同じRawの二重適用を、内容hashと冪等keyで防ぐ。
- 非公開、個人用、認証付き、保存条件不明のRawは、HESTIAの受領確認後にKURA側で消去する。
- 秘密値そのものを受渡契約、Raw、ログ、台帳へ含めず、必要時は秘密参照だけを使う。
- KURA停止、配達遅延、保存失敗を、正常取得として扱わない。
- 即時イベント処理、機器制御、安全停止はKURAの応答や保存完了を待たない。
- 既存Collectorは、結果、hash、時点、欠損、停止時動作の比較が完了するまで削除しない。

KURA初期版へ、HESTIAの正規化、判断、ExecutionGate、実機操作、現在状態DB、
実行待ち命令、認証値の無条件移管を行わない。

## リリース段階

### Phase 0: 正本・範囲・状態表示の確定

目的は、未実装、オフライン実装、実機適格、本番稼働を混同しないことである。

- `system-philosophy.md`と四層文書を設計の正本として確認する。
- Integrationごとに、Reader、Collector、Executor、実機試験、常駐状態を分けて一覧化する。
- v1.0必須、条件付き、延期の三分類を付ける。
- 家庭固有ID、秘密、実データをGit管理文書へ書かない。

**完了条件:** 一つの機能表から、現在できることと未確認事項を誤解なく判別できる。

### Phase 1: 共通契約とOS非依存境界

- Observation、品質、欠損、時刻、鮮度の共通契約を固定する。
- ReaderとExecutorの公開interfaceを分離する。
- timeout、retry、重複排除、結果不明、手動介入の共通規則を固定する。
- OS固有のscheduler、秘密注入、service管理をcoreとAdapterから分離する。
- 新しいAdapterが共通契約試験を再利用できる状態にする。

**完了条件:** 匿名fixtureに対する主要契約試験がmacOSで成功し、OS固有のservice、
秘密注入、保存先が交換可能なportの外側へ隔離されている。LinuxとWindowsの実行試験は、
移行先が確定した時点の再適格化項目として追跡する。

### Phase 2: 第1層・読み取り経路の適格性確認

対象ごとに、単発、短時間、24時間の順で確認する。全機器を一括昇格しない。

- FusionSolar / SmartLogger
- SwitchBot
- Smart LEDZ
- エコキュート
- Qrio
- Miele@home
- BRAVIA
- 日産サクラ
- 北陸電力料金情報などの外部公開情報

イベントが利用できる場合はイベントを主経路とし、低頻度snapshotで正しさを回復する。
連続値、離散状態、イベント、定義情報で取得周期と保存方法を分ける。

**完了条件:** 対象ごとに、取得周期、容量上限、停止方法、欠損回復、Schema変更検出、
秘密非露出、機器標準機能への無影響が確認される。

### Phase 3: 第2層・保存、容量、復元

- current state、state interval、event ledger、continuous series、
  observation coverageを区別する。
- 同一の離散状態を無制限に追記しない。
- 高頻度連続値はrolling bufferと集約を分ける。
- 長期Rawはchecksum付き可逆圧縮と隔離復元試験を使う。
- 保存クラス、保持期間、日次増加量、削除条件をデータ辞書へ記録する。
- 正本と別障害領域に、検証可能なバックアップを用意する。

**完了条件:** 容量不足でも以前の正常バックアップを壊さず、RawアーカイブとDBバックアップを
区別して復元できる。実データ削除は別媒体複製と個別承認なしに起きない。

v1.0では2026-07-30の利用者承認により、30日容量評価の完了をrelease blockerにしない。
匿名容量probeをリリース後も継続し、問題が判明した場合は自動削除や無承認の保持短縮ではなく、
別の設計変更として容量、保存粒度、archive、DB分離を見直す。

### Phase 4: 即時イベント経路と非同期経路

- Adapterからアプリ内イベント処理への即時配達を、保存より先に行う。
- 利用者・規則・イベントからの全操作を、保存や集計を待たない即時実行経路へ載せる。
- 保存、集計、Raw転送、監査を独立した有界キューへ分離する。
- 順序、重複排除、上限付き再送、背圧、timeout、失敗状態を共通化する。
- キュー混雑、KURA停止、保存障害がExecution判断を遅らせないことを確認する。
- SwitchBot人感→Smart LEDZを最初のオフライン実証とする。

**完了条件:** 保存を意図的に遅延・失敗させても、即時経路が設定した上限内で完了または
明示的に安全停止し、イベントの欠落や二重操作を隠さない。

### Phase 5: 第3層・説明可能な最小判断

- 安全、健康、快適性、経済性、利用者指示を区別する。
- 不確かな入力、古い値、欠損値で断定しない。
- 判断頻度を上げる場合も、操作回数と不安定化に上限を設ける。
- 根拠、予測範囲、判断しない理由、代替案を残す。
- 汎用ルールエンジンより、価値を実測できる少数の縦切りを優先する。

**完了条件:** 採用、見送り、判断不能の理由を、入力時点と規則versionから再現できる。

### Phase 6: 第4層・ExecutionGateと操作適格性

- Intentの権限、期限、対象、能力、鮮度、品質、重複、手動介入を検査する。
- 指示受付後は、最新のメモリ内証拠と長寿命sessionを使い、最小限のGate後すぐ送信を開始する。
- 能力ごとに指示受付から最初の送信試行までの遅延上限を決め、実測する。
- Adapter直呼びを本番経路から禁止する。
- `requested`、`accepted`、`verified`、`outcome`を一つの成功値へ潰さない。
- timeoutや結果不明後に、鍵、給湯、車両等の危険操作を盲目的に再送しない。
- Shadow、単発実機、短時間監視、半自動審査の順を守る。
- Smart LEDZは、現在値から目標の明るさ・色温度へ指定時間で段階変更できるようにし、
  最初の変化を即時送信、未送信の旧値を集約、手動操作時は残りを破棄する。

**完了条件:** 能力ごとに復旧方法と停止条件があり、実機試験台帳へ結果が残り、
未確認能力が本番で実行されない。

### Phase 7: 利用画面、通知、運用負担

- 画面は現在値、品質、更新時刻、判断理由、操作結果を混同せず表示する。
- 警告は継続中、復旧、次の行動を示し、同じ障害を無制限通知しない。
- 太陽光・蓄電池は時系列と電力の流れをグラフで確認できる。
- 利用者が停止、手動優先、再同期、対象別無効化を理解できる。
- 管理作業に費やす時間と通知数を測る。

**完了条件:** 日常利用者がログや内部IDを読まずに、状態、問題、必要な行動を判断できる。

### Phase 8: セキュリティ、障害訓練、リリース判定

- 秘密検査、依存関係、権限、ログ、バックアップ、復元を確認する。
- HESTIA停止、DB読み取り不能、ネットワーク断、クラウド断、Schema変更を模擬する。
- 再起動時に古い状態や未完了Intentを自動再生しない。
- 24時間監視後、必要な経路だけを限定的に長期監視する。
- release blocker、既知制限、rollback、連絡・保守手順を文書化する。

**完了条件:** チェックシートの必須項目がすべて証拠付きで合格し、延期項目が
v1.0の安全性や主要価値を損なわないとレビューされる。

### Phase 9: v1.0後のKURA最小実証

初回は、実機制御や認証付き個人Rawを対象にしない。更新頻度があり、公開情報で、
失敗しても住宅制御へ影響しない一つの情報源を選ぶ。

1. HESTIAの現行CollectorとKURA版Connectorを期限付きで並行稼働する。
2. Raw境界、内容hash、資料時点、欠損、訂正、取得停止を比較する。
3. HESTIAの正規化結果が同じになることを匿名fixtureと固定Rawで確認する。
4. KURA停止時に現行経路または明示的なstale表示へ戻れることを確認する。
5. 受領確認、重複配達、再送上限、非公開Raw消去を契約試験で確認する。
6. 合格後も、既存Collector削除と資格情報移行を別々に承認する。

北陸電力の公開料金・燃料費調整・補助情報は、初回候補として適している。
リアルタイム制御に使うSwitchBotイベント、Qrio、給湯、車両、認証付きクラウドは、
初回実証の対象にしない。

## 共通開発運用標準 v1.0（正本）

**名称:** 品質優先・根拠ゲート型・キュー駆動開発
**適用先:** HESTIAの01_相談・設計、02_実装・検証、サブエージェント
**優先関係:** 利用者の個別指示、明示承認、法令、安全要件を本標準より優先する。

本節をHESTIAにおける共通開発運用標準の唯一の正本とする。同じ本文をREADME、DESIGN、
AGENTS、毎夜の指示へ複製しない。必要な文書からは本節を参照する。

### 評価優先順位

1. 品質と見落とし防止
2. 完了時間
3. 全AIの実測トークン
4. 往復、追加取得、手戻り
5. Mac負荷

先順位を悪化させ、後順位だけを改善する方式は採用しない。

### 作業単位とTask Contract

一つの目的と検証可能な完了条件を一作業とする。目的または完了条件が変わる場合は、
同じ作業へ追加せず、新しい作業へ分ける。

01_相談・設計は、利用者が示した作業ID、完了条件、承認IDを基に、次をTask Contractへ
補完してから実装へ渡す。

- 目的、変更範囲、変更禁止範囲
- 維持すべき不変条件、危険度
- 承認済み操作と承認期限
- 検証方法、停止条件
- 担当モデル、所有ファイル
- Evidenceの取得・受渡経路

### 三つの実行経路

| 経路 | 適用条件 | 既定の進め方 |
|---|---|---|
| 直接 | 対象、修正、testが既知で、小さく可逆かつ低リスク | Philipを使わず、最も軽い適格担当で局所実施 |
| 標準 | 探索、複数ファイル、継続作業、Evidence共有が有効 | 01がPhilipを一度prepareし、最も軽い適格担当が実装し、01がdeltaと差分をレビュー |
| 高保証 | 設計、共有基盤、公開契約、security、認証、権限、DB、削除、外部API、実機、金融・安全計算、影響不明 | Philip、高性能モデルによる原典確認、必要な全検証、人間の承認 |

迷う場合は一段安全側の経路へ送る。

HESTIAでは、安全制御、家庭内LAN、実機、高影響機器、エネルギー設備、健康・防災、
書込みExecutor、共通DB、launchd、認証、外部クラウドを固有の高保証対象とする。
ReaderとExecutorを分離し、実機操作を明示承認なしに実行しない。

### 役割と担当モデル

- **人間:** 価値、優先順位、高影響操作を決定・承認する。
- **01_相談・設計:** 高性能モデルを使い、Task Contract、経路、危険度、担当、最終レビューを決める。
- **Philip:** Snapshot、Evidence、reference/delta、関連test計画、隔離検証、秘密検査、測定を支援する。
- **02_実装・検証／サブエージェント:** 確定した範囲だけを実装・検証し、仕様を広げない。
- **Luna非常に軽い:** 置換、整形、明示済み文書、command、log整理を担当する。
- **Luna軽い:** sufficientな根拠に基づく局所実装、既知pattern、test追加を担当する。
- **Terra中程度:** 複数箇所の統合、debug、partialの解消を担当する。

指定した担当が利用できない場合は、同等以上の安全性を持つ利用可能な担当へ送る。
実装者は自分の成果を最終承認しない。

### Evidenceゲート

- 同一作業では、原則として初回fullを一回、実装後deltaを一回だけ取得する。
- ACKはEvidence本文を実際に受信した後だけ行う。
- referenceは、受信済みbaseを保持する担当だけが利用する。
- Snapshot鮮度、明示ファイル、完了条件ごとの設計・実装・test、反証、影響範囲、
  unresolved、矛盾、omitted候補を確認し、`sufficient`表示だけを盲信しない。
- `partial`はrecommended queryによる限定取得を一回行う。それでも不足する場合はprepareを
  反復せず、01またはTerraが原典を確認する。
- `insufficient`、`stale`、重大な矛盾がある場合は実装を開始しない。

### 実装と並列化

原則は一つの書込み系統とする。依存関係と統合時間を含めても短縮でき、所有ファイルが
分離できる場合だけ、書込みを二系統にする。三系統目はread-onlyのEvidence取得または
検証準備に限定する。統合担当は一人とし、同じファイル、DB、共有状態を同時変更しない。

担当へ渡すのはTask Contract、必要なFact ID、所有ファイル、検証、停止条件だけとする。
範囲外の整理、testの削除・弱体化、未承認操作を禁止する。

### 検証

検証担当を一人に固定し、同じtestの重複実行を避ける。実装中の局所test、統合後の関連test、
最終の既存必須品質ゲートを、それぞれ必要な時点で一度実行する。高リスク、共有基盤、
関連testが不明な変更は全testへ昇格する。

コード変更では差分検査と秘密検査、振る舞い変更では回帰testを原則必須とする。
Themisの選択testは中間反復の削減に使えるが、既存の最終ゲートを置き換えない。
Failure Fingerprintでlogを圧縮する場合も、確認可能な原logへの参照を残す。

### 完了状態

- **DONE:** 完了条件100%、必須検証100%、新規Critical/High未解決0、最新Snapshot/delta、
  秘密違反0、01の意味レビュー完了。
- **READY_FOR_APPROVAL:** 安全な実装と検証が完了し、外部反映等の承認を待つ状態。
- **CHECKPOINTED:** 時間切れまたは担当切替。成功済み検証と再開情報を保存した状態。
- **BLOCKED:** 安全に継続できない状態。未完成をDONEにしない。

返却は変更差分、test結果、判断待ちを基本とし、生log、秘密値、会話全文を返さない。

### 不在運転

利用者が実際の離席意図で「行ってきます」「おやすみ」または同趣旨の不在を明示し、
既存Task Contractと承認済みREADYキューがある場合だけ発動する。引用や説明文では発動せず、
新しい機能、対象、完了条件、承認範囲を推測して作らない。

進行順は、クリティカルパス、他作業を解放する前提、短い独立作業、検証、文書・翌朝準備とする。
一系統が承認待ち、仕様判断、環境問題で止まった場合は、その系統だけをCHECKPOINTEDにし、
他の安全なREADY作業を続ける。重い全testまたはbuildはMac全体で原則一系統だけ実行する。

承認済みの読み取り、指定編集、ローカルtest/build、秘密検査、差分検査、一時環境、
承認済みcommitは工程単位で進める。未承認のpush、merge、release、deploy、DB・本番データ変更、
削除、依存追加・更新、外部書込み、実機、家庭内LAN、認証、OS・機器設定、現役環境への導入は
行わない。必要事項は対象、影響、rollback、検証、必要承認を一件に集約し、無関係な作業を
止めない。

「戻りました」「おはよう」「不在運転終了」または同趣旨の復帰で解除し、01がdelta、差分、
受入条件を一括レビューする。安全なREADY作業が尽きた場合は、勝手に新機能を作らず停止する。
将来時刻の再確認または定期実行が必要な場合だけAutomationを利用する。

承認待ちの一般原則は
[`full-system-review-20260725.md`](../reviews/full-system-review-20260725.md#承認待ちの扱い)
を参照する。

### 測定と改善

失敗、再試行、救済を含め、品質、wall-clock、全Agentの実測token、往復・取得・手戻り、
Mac負荷を記録する。取得できない値は`null`とし、推測で補わない。初回fullと継続時の
reference/deltaを分けて測定する。

完了条件100%、Critical/High見落とし0を満たした方式だけを速度比較の対象にする。
比較可能な10件で、中央値が10%以上改善し、p90を10%以上悪化させず、かつ実測tokenを
15%以上削減した場合を暫定採用の目安とする。20件でroutingを更新する。
重大な見落としが一件でも起きた場合は、該当する自動軽量経路を停止して原因を確認する。

## v1.0のリリース阻害条件

次のいずれかが残る場合、v1.0正式運用へ進めない。

- 秘密値、家庭固有ID、個人データが通常ログ、fixture、Gitへ出る。
- 実行受付だけを物理結果の成功として表示する。
- 結果不明の危険操作を自動再送する。
- HESTIAまたはKURA停止により、機器標準の安全機能や物理操作が使えなくなる。
- 観測不能と同一状態を区別できない。
- 無制限retry、無制限queue、無制限Raw保存がある。
- 復元試験をしていないバックアップだけを根拠に現役データを削除する。
- 未適格のReaderまたはExecutorが本番経路へ接続される。
- 実機変更、DB切替、常駐化、秘密移行を、対象とrollbackの確認なしにまとめて行う。

## 正本と更新規則

- 進捗の正本は`hestia-v1-checklist.md`とする。
- 項目を完了にする時は、日付、証拠、確認者を記載する。
- コード追加だけで、実機適格、本番配備、長期安定を完了扱いにしない。
- 仕様変更、機器firmware変更、KURA契約変更時は、影響するGateを再開する。
- 半年ごと、または重大障害後に、ロードマップと保存方針を再レビューする。
- 共通開発運用と不在運転の恒久規則は、本書の「共通開発運用標準 v1.0（正本）」だけで管理する。
