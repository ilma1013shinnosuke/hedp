# HESTIA v1.0 運用・停止・復旧手順

## 目的

この文書は、HESTIAを家庭で運用する際の開始、停止、障害対応、再起動、
rollbackを一か所にまとめる正本です。機器メーカーの安全機能、物理操作、
既存scheduleをHESTIAより優先します。

HESTIAが停止しても生活に不可欠な機能が失われないことを前提とします。
HESTIAだけに依存する能力は、個別の安全な停止状態と代替手段が確認されるまで
本番能力へ昇格しません。

## 運用開始前の必須確認

1. `hestia-v1`リリース検査が合格している。
2. 本番対象能力が`live_qualified`または`deployed`である。
3. 対象能力の匿名化済み適格性証拠とrollback手順がある。
4. 秘密情報、家庭固有値、実機RawがGitや通常ログに含まれていない。
5. DB、Raw保存先、空き容量、backupの直近状態を確認した。
6. 未認定Executorの既定値が`disabled`または`shadow`である。
7. 利用者が保証範囲と既知制限を承認している。

一つでも満たさなければ、家庭向け正式運用を開始しません。Readerの限定運用、
fixture試験、shadow判定は、その範囲を明示して継続できます。

## 起動

1. 現在の機器状態をReaderから新規取得する。
2. 欠損、古い値、未知値、Schema不一致を正常値として扱わない。
3. 保存されていた前回状態や未完了Intentを機器へ適用しない。
4. Readerの品質と時刻が適格性条件を満たした能力だけを有効にする。
5. Executorは能力ごとの承認、ExecutionGate、期限、重複確認を通す。
6. 起動後の最初の操作は、受付、送信試行、read-back、最終結果を確認する。

再起動は「前回の続き」ではなく、外部世界を再観測してから新しく開始します。

## 通常運用

- 即時操作は保存、集計、KURA、外部archiveの完了を待たない。
- 監査と保存は別の有界queueで処理し、混雑を明示する。
- 取得不能は`0`、空文字、前回値で埋めない。
- 結果不明の操作を成功と記録しない。
- 人の操作を優先し、手動介入後は能力ごとの待機時間を守る。
- 同じ警告を無制限に通知せず、継続中と復旧を関連付ける。
- 能力ごとのtimeout、retry、確認期限、停止条件を超えない。

## 安全停止

次のいずれかで、対象能力への新規自動操作を停止します。

- 現在状態を十分な品質と鮮度で確認できない
- 認証、Schema、対象機器、権限が想定と一致しない
- queue、保存、DB、network障害が設定上限を超えた
- 操作結果が不明で、再送に副作用の可能性がある
- 人が手動操作または停止を指示した
- 実機の警報、安全機能、メーカー保守と競合する

停止時は、未送信の即時操作を破棄し、古いIntentを永続queueへ移しません。
可能な範囲で現在状態をread-onlyで再取得し、原因、影響範囲、次の行動を
秘密値なしで記録します。

## 障害別の扱い

### Reader・通信障害

対象値を`missing`または`stale`として扱い、最後の正常値を現在値として
使いません。上限付き再試行後も回復しなければ、その情報に依存する判断と操作を
停止します。他の独立Adapterは継続できます。

### DB・保存障害

即時経路を保存完了待ちにしません。ただし監査証拠を安全に残せない高影響操作は
開始しません。保存queueの上限到達を明示し、無制限にmemoryやdiskを消費しません。

### KURA・外部archive障害

HESTIAの観測、判断、安全停止、即時操作を継続可能な構造とします。Raw転送は
別queueで保留または上限付き失敗とし、KURA回復を操作開始条件にしません。

### Schema・未知値

既知値へ推測変換しません。Rawを保全できる場合は原文を残し、正規化結果を
`invalid`または`unknown`にします。該当Adapterだけを隔離します。

### 実行結果不明

自動再送しません。受付結果、送信時刻、read-back期限を残し、利用者へ
「結果不明」と次の確認方法を示します。鍵、給湯、車両、発電・蓄電池などの
高影響能力は人の確認へ戻します。

## 再起動後の復旧

1. 未送信の即時sessionとmemory上のtimerが空であることを確認する。
2. 保存された古いIntentを自動で再投入しない。
3. 各機器から現在状態を再取得する。
4. 操作中だった可能性がある能力は、結果を推測せず`unknown`とする。
5. 手動操作、機器標準schedule、安全機能の状態を優先する。
6. 原因が解消したAdapterだけを一つずつReaderから復帰する。
7. Executorの復帰は、新しいIntentと新しい承認で行う。

## Rollback

Rollbackはデータ削除や機器設定初期化ではなく、HESTIAの新しい能力を停止し、
直前に確認済みの安全な構成へ戻す操作です。

1. 対象Executorを`disabled`または`shadow`へ戻す。
2. 新規自動Intentの受付を止め、未送信操作を破棄する。
3. 機器の標準機能、物理操作、既存scheduleを維持する。
4. DBとRawは削除せず、変更前後の境界時刻を記録する。
5. Readerは安全なread-only範囲に限定して状態を確認する。
6. 直前の確認済みreleaseへ戻し、関連試験とリリース検査を再実行する。
7. 原因、影響、復旧時刻、残る不明点を記録する。

機器設定、家庭LAN、認証、現役DB、常駐設定を戻す必要がある場合は、この一般手順
だけで実行せず、対象、影響、具体的な復元方法を確認して明示承認を得ます。

## 緊急停止

利用者が停止を指示した場合、価値判断より優先して新規自動操作を停止します。
ただし、停止処理そのものがメーカーの安全機能や機器標準動作を妨げてはいけません。
緊急停止後の再開は、自動ではなく現在状態の再観測と利用者承認を必要とします。

## 証拠と個人情報

運用証拠には、試験日時、能力ID、結果、遅延、品質、失敗理由、復旧結果を残します。
秘密値、家庭内IP、SSID、MAC address、家庭固有ID、認証済み画面、個人情報は
リリース文書やGitへ記録しません。実機証拠は匿名化し、元データは承認された
安全な保管場所だけで扱います。

## 現在の既知制限

- v1.0の保証候補範囲は承認済みだが、release candidateの最終承認は未完了。
- FusionSolar / SmartLogger read-onlyは単発、短時間、欠損許容条件付き24時間が
  合格済み。2026-07-30の再試験で正確な開始・終了時刻を持つ構造化manifestも完成。
- その他のReaderはv1.0保証対象外で、実機適格性は未完了。
- Executorの実wire送信、read-back、遅延上限は能力ごとの確認が必要。
- v1.0 read-only能力の常駐process、隔離DB利用不能、TEST-NET通信断、
  Schema変更、再起動訓練は完了済み。
- launchd切替失敗時のlegacy job復元は隔離fixtureで合格し、現役read-only jobも
  2026-07-30にrollbackを有効にした状態で停止・再起動・新規観測を確認した。
- OS非依存の暗号化秘密正本は未確定。
- 別障害領域backupは利用者が同時喪失リスクを受容し、v1.0必須条件から延期した。
- 30日容量評価は利用者承認によりリリース後へ延期し、匿名容量probeを継続する。
- sanctumの配置・復旧要件は`docs/release/hestia-v1-sanctum-readiness.md`へ固定したが、
  実配置、鍵復旧、外部snapshot・restoreは未実施。

これらが残る間は、HESTIAを家庭向け正式版とは表記しません。
