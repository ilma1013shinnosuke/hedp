# HESTIA v1.0 運用保証方針

## 保証の意味

HESTIAの運用保証は、全機能が動くという宣言ではありません。保証対象として
選定した能力だけについて、実機適格性、障害時動作、監視、復旧、rollbackを
客観的な証拠で確認し、その範囲を明示することです。

コード、匿名fixture、単体テストだけでは、家庭の実機で常時利用できるとは
判定しません。未認定のReaderとExecutorは、既定で無効またはshadowに置きます。

## 二つの保証

### Platform保証

- 四層の責任が分離されている
- ReaderとExecutorが分離されている
- 欠損、未知値、古い値を正常値として扱わない
- 即時経路が保存、集計、KURAを待たない
- retry、queue、保存量に上限がある
- 再起動時に古いIntentを自動再生しない
- HESTIA停止時も、機器標準機能と手動操作を妨げない

### Capability保証

各ReaderとExecutorを個別に認定します。認定には、少なくとも次が必要です。

1. 対象と操作範囲
2. 単発、短時間、24時間の読み取り適格性
3. 低リスク操作の受付、最初の送信、read-back、結果確認
4. timeout、結果不明、停止条件
5. 手動操作の優先
6. 復旧とrollback
7. 匿名化済みの適格性証拠

一つの能力を認定しても、同じ機器の別能力は自動的に認定しません。

## 自動判定

`config/release/hestia-v1.json`を保証対象の機械可読profileとします。
`scripts/check_release_readiness.py hestia-v1`は、次をread-onlyで検査します。

- 保証対象範囲の承認
- 必須Gateの完了
- 必須運用文書
- 本番能力の実機適格性
- 安全な実行既定値
- release時のrollback検証

一つでも不足すれば不合格です。不合格でも、開発やshadow試験は続けられますが、
家庭向け正式版とは呼びません。

実機能力を保証対象へ加える場合、単なる証拠文書の存在では合格にしません。
`production_capabilities`の各能力には、匿名化済み補足文書に加えて
`qualification_manifest`を指定します。manifestは
`config/release/qualification-evidence.example.json`と同じ契約を使い、
次をすべて満たす必要があります。

- 能力IDが一致する
- read-only試験である
- 単発、短時間、24時間の三段階がすべて合格している
- 各段階に開始・終了時刻と1件以上のsampleがある
- 設定変更、秘密情報混入、機器への悪影響がない
- 匿名集計結果のSHA-256がある

Raw本文、IP、機器ID、認証値、家庭固有名称はmanifestへ記載しません。
未完了の段階、匿名化されていない証拠、コード・fixtureだけの証拠は
`live_qualified`として受理しません。

## 障害時の原則

- 取得不能を0や前回値で埋めない
- 保存障害を即時操作へ波及させない
- 結果不明の危険操作を自動再送しない
- 実行不能を第3層へ明示し、同じIntentを無限に往復させない
- HESTIA停止中は、機器標準機能、物理操作、既存scheduleを維持する
- 復帰時は機器から現在状態を再取得し、保存した古い状態を適用しない

## 昇格手順

能力は`fixture_only`、`reader_only`、`shadow_only`から始めます。試験証拠を
確認した能力だけを`live_qualified`へ上げ、運用監視と復旧を確認して
`deployed`へ上げます。昇格は一段ずつ行い、文書、profile、適格性証拠を同時に
更新します。

## 現在の扱い

現在のprofileはrelease candidateです。2026-07-28に、macOS上の
FusionSolar / SmartLogger read-only収集だけをv1.0の最小保証候補とする範囲が
承認されました。単発・短時間の実機試験に加え、2026-07-29には利用者承認済みの
欠損許容条件で24時間の運用履歴も合格しました。ただし、構造化manifestの最終化、
必要な長期監視、復旧、rollbackは未完了です。

2026-07-30に単発・短時間段階を同じ有限read-only条件で再実施し、構造化manifestへ
正確な開始・終了時刻を統合しました。三段階の証拠が揃ったため、対象能力は
`live_qualified`候補としてprofileへ登録済みです。復旧・長期監視等が完了するまで
`deployed`へは昇格しません。

30日容量評価は、2026-07-30の利用者承認によりv1.0のrelease blockerから外し、
リリース後の継続監視へ移しました。容量probeと上限は維持し、問題時も自動削除せず、
別の設計変更として保存方式を見直します。

このため、自動判定は引き続き意図的に不合格になります。これは故障ではなく、
範囲承認と運用保証を混同せず、未検証の能力を本番へ混入させない安全動作です。
