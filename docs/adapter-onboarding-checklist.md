# 新規Adapter追加チェックリスト

## 使い方

本書は[Adapterのライフサイクル](adapter-lifecycle.md)を実作業へ落とすチェックリストである。
機器を買った、アプリを解析した、公開APIを見つけた、という事実だけでは実装を開始しない。
各Gateの必須項目を満たしてから次へ進む。
[SumiCore Project](../PROJECT.md)のVision、価値の優先順位、成功条件を上位基準とする。

運用状態は次の順で上げる。

```text
research → observation → read_only → limited_execution → production
```

`degraded`、`deprecated`、`retired`は通常運用から外す状態である。状態はAdapter全体ではなく、
確認した機種・版・能力の範囲で宣言する。

## Gate 0: 追加目的

- [ ] メーカー、製品名、型番を特定した。
- [ ] 確認できるアプリ、firmware、API、protocolの版を記録した。
- [ ] 欲しい状態、イベント、現在プラン、予約、動作中内容を列挙した。
- [ ] 将来必要な操作を、読み取りと分けて列挙した。
- [ ] 既存Adapter、DB、外部連携との重複を確認した。
- [ ] SumiCoreが停止しても残る機器標準機能を記録した。
- [ ] 追加する利用価値と、作らない機能を説明できる。
- [ ] 減らしたい生活上の負担と、成功を確認する方法を決めた。
- [ ] 増える通知、保守、認証更新、障害対応の負担を見積もった。
- [ ] 期待する利益が運用負担を上回らない場合の中止条件を決めた。

成果物:

```text
docs/integrations/<vendor>/README.md
```

## Gate 1: 公開情報と試験計画

- [ ] 公式仕様、説明書、API、通信規格、認証、制限を調査した。
- [ ] 公式、実機、第三者実装、推測・未確認を区別した。
- [ ] 状態、イベント、予約、操作、設定変更を区別した。
- [ ] 読み取り試験の対象、回数、時間、容量上限を決めた。
- [ ] 中止条件、影響、復旧方法を決めた。
- [ ] 削除、初期化、再登録、network変更、firmware更新、校正、Webhook変更、
      認証変更を承認必須として残した。
- [ ] 調査ファイルを`runtime/research/<vendor>/<date-topic>/`へ隔離した。
- [ ] `.env`、暗号化正本、家庭固有設定、実Rawの保存場所を決めた。

成果物:

```text
docs/integrations/<vendor>/research.md
docs/integrations/<vendor>/safety.md
```

## Gate 2: 隔離した読み取り観測

- [ ] 現役DBへ保存せず、read-onlyまたはShadow Modeで観測した。
- [ ] field、型、単位、範囲、enum、時刻を実測した。
- [ ] 取得周期、遅延、欠損、重複、offline時の応答を実測した。
- [ ] Raw一件、一日、一年の容量を見積もった。
- [ ] API、機器、家庭LANへの負荷を確認した。
- [ ] 未知fieldと解析不能Rawを上限付きで保全した。
- [ ] 想定外の状態変更、通信急増、警告が起きていない。

このGateで操作命令を送信しない。

## Gate 3: データ契約とfixture

- [ ] 共通名とメーカー元fieldの対応を記録した。
- [ ] `observed_at`と`received_at`を区別した。
- [ ] 欠損を0、空文字、前回値で埋めていない。
- [ ] `good`、`stale`、`missing`、`invalid`、`estimated`、`unknown`を表現できる。
- [ ] 正常、欠損、異常、未知field、timeoutの匿名fixtureがある。
- [ ] fixtureから家庭、個人、機器を再特定できない。
- [ ] Raw、正規化値、event、監査記録を重複保存していない。
- [ ] 保存クラス、粒度、期間、圧縮、削除Gateを決めた。

成果物:

```text
docs/integrations/<vendor>/data-dictionary.md
tests/fixtures/<vendor>/
```

## Gate 4: 読み取りAdapter

- [ ] transport、reader、normalizer、capability、error mappingの責任が分かれている。
- [ ] readerからexecutorをimportしていない。
- [ ] timeout、再試行回数、総時間に上限がある。
- [ ] retryはread-onlyかつ冪等な処理だけに限定した。
- [ ] 秘密値、生の家庭固有ID、実Raw本文を通常ログへ出さない。
- [ ] Rawから正規化値まで根拠を追跡できる。
- [ ] 現役DB、実API、実機なしで単体試験できる。
- [ ] Schema変更と未知版を既知として扱わない。
- [ ] 読み取りによって機器状態が変化しない。
- [ ] 全テスト、静的検査、秘密検査が成功した。

操作が不要なら`read_only`で完成とする。

## Gate 5: 操作の価値審査

- [ ] 純正機能では実現できない価値がある。
- [ ] 機器横断連携または自動化の利益を説明できる。
- [ ] 手動操作と機器標準scheduleを妨げない。
- [ ] 受付、実行、実状態を区別して確認できる。
- [ ] SumiCore停止時の安全な代替動作がある。
- [ ] 結果不明、通信断、再起動時の扱いを定義した。
- [ ] 運用負担が利益を上回らない。

一つでも満たせない場合、executorを作らない。

## Gate 6: 能力単位の操作契約

操作は機器単位で一括承認せず、能力ごとに定義する。

- [ ] 絶対指定、相対変更、Trigger、設定変更を区別した。
- [ ] 危険度と自動化区分を決めた。
- [ ] 対象、期待状態、前提条件、有効期限を定めた。
- [ ] timeout、再試行、重複抑止を定めた。
- [ ] 指示受付から最初の送信試行までの遅延上限を、能力ごとに定めた。
- [ ] 保存、集計、Raw転送、詳細監査、画面更新を待たない即時経路を使用する。
- [ ] 操作受付後の機器探索や全状態再取得を避け、必要な状態証拠を事前更新する。
- [ ] 受付確認とread-back方法を定めた。
- [ ] 手動操作との競合と一時停止条件を定めた。
- [ ] 結果不明時の自動再送可否を定めた。
- [ ] 再起動後に未送信操作を再生しない。
- [ ] 元へ戻す方法と、戻せない影響を記録した。

成果物:

```text
docs/integrations/<vendor>/capabilities.md
docs/integrations/<vendor>/runbook.md
```

## Gate 7: 操作の段階試験

- [ ] 模擬応答だけのオフライン試験
- [ ] 命令を送らないShadow Mode
- [ ] 対象を一台に限定した利用者承認付き試験
- [ ] 実状態のread-back
- [ ] 指示受付から最初の送信試行までの遅延を実測し、能力別上限内である。
- [ ] 保存や非同期処理を意図的に遅延・失敗させても送信開始が遅れない。
- [ ] timeout、重複、通信断、再起動試験
- [ ] 手動操作時の停止試験
- [ ] 時間、回数、対象を限定した運用
- [ ] 実績を得た低リスク能力だけを通常運用

第3層は価値を判断し、第4層は許可の有効性を検査して実行・確認する。Adapterの
`executor.py`はメーカー固有送信と応答整理だけを担当する。

## Gate 8: 配備と継続監視

- [ ] 対応版、最終確認日、根拠、再確認条件を公開した。
- [ ] 取得成功率、遅延、欠損、認証期限、Schema変化を監視する。
- [ ] Rawとログの日次増加量に上限がある。
- [ ] 一つのAdapter障害が他メーカーへ波及しない。
- [ ] 未配備・Shadow・本番の状態を利用者が判別できる。
- [ ] rollbackと停止手順がある。
- [ ] 長期間停止後は現在状態を再取得してから再開する。
- [ ] 利用者が対応する通知件数と保守作業を観測できる。
- [ ] 目的とした生活上の負担が実際に減ったかを見直す期限がある。

## 更新・廃止

次の場合は少なくともread-only回帰試験へ戻す。

- アプリ、firmware、API、SDK、protocolが変わった。
- 認証、endpoint、Gateway、network経路、機器を変えた。
- 未知field、未知enum、Schema不一致、遅延変化を検出した。
- 長期間停止したAdapterを再開する。

廃止時は、新規操作、未完了操作、定期取得、他機能参照の順に停止する。能力表、
データ辞書、障害知見、最終対応版だけを知識として残し、同じcodeをGitとarchiveへ
重複保存しない。実Rawや履歴の削除は別承認とする。

## Pull request確認欄

- [ ] 変更対象と対象外が説明されている。
- [ ] 読み取りと操作が別module・別公開interfaceである。
- [ ] 実値を含まないfixtureと失敗系testがある。
- [ ] timeout、retry、欠損、品質、結果不明が明示されている。
- [ ] 操作は共通即時経路を使い、能力別の送信開始遅延上限と実測結果がある。
- [ ] 保存量と保持期間が説明されている。
- [ ] versionと再確認条件がある。
- [ ] 秘密、家庭固有値、実Raw、DB、log、screenshotがGitにない。
- [ ] SumiCore停止時も機器の基本機能が残る。
- [ ] rollback、停止、廃止が可能である。
- [ ] 追加による利益と、利用者へ増える負担を両方説明できる。
